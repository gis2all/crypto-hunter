# 一轮的编排

`pipeline/` 把一轮跑完（`collect` / `decide` / `states` / `progress` / `run` / `schedule` / `write`）；纯逻辑在 `core/`（`filters` / `funnel` / `scoring` / `models` / `parse` / `caliber`），那里不应有 IO。

## 硬过滤

先免费后花钱：第一半只放**粗筛行就能定**的规则，缺的数先按 `MARKET_ENRICH` 补齐，再跑第二半。两半的分界是「这个数是不是每个源答得一样」，而不是「是否需要付费」。第二半必须对每一行给出判决，所以补齐默认覆盖**整个过关池**（`gate_limit: 0`）。

| 规则 | 说明 / 反例 |
| --- | --- |
| universe 的主源是「池」不是「币」（Arc 没有 token 级列表端点）；适配器在拉取侧就按 `filters.is_empty_shell` 剔掉空壳行。 | RadarDEX 的 `sort=mcap` 不是全链排名，它的市值口径与 GMGN / GeckoTerminal 并不一致。 |
| 阈值都在 `config/chains/*.yaml` 的 `pipeline.prefilter`，但**分两半跑**：第一半只剩市值区间与空壳淘汰（`require_market_data` 默认开 —— 市值与流动性**同时**缺失即淘汰，reason 是 `empty_shell`），流动性 / 24h 成交下限、持有人区间、Top10 / 捆绑上限在第二半。**持有人是区间**：上下限共用一条规则，`holders_max` 缺键即无上限。 | 市值留在第一半，是因为它在 GMGN / DexScreener 两家按美元一致，流动性 / 成交不一致 —— 第一半的判决是终审，不能拿没校准的读数开判。下限压到 1 万是为了不漏刚起步那批（Arc 上 85% 的币停在发射台 5000–9000 U 的初始 FDV）。反例：老快照缺 `require_market_data` 键，一轮把四千个空壳行判成「未知即通过」。 |
| 零数据淘汰：五个排序因子全部缺失的行按 `missing_data` 淘汰（无法参与打分）。**只在富集之后判**，关掉用 `prefilter.min_scored_fields: 0` 或缺键。它和空壳淘汰是两个 reason。 | 富集前空字段的含义是「粗筛没带这个字段」，放进第一半会把整批行误淘汰。 |
| **未判定永不淘汰**：整源缺失记 `None`，既不判通过也不判淘汰 —— 所以凡是要读单个币才能定的数都只能放第二半。 | 反例：两半合成一次，未知等于放行，上千个发射台自报的行直接进池。 |
| 补齐链上数据是独立的一次：补谁由 `_needs_chips` 定（缺持有人 / Top10 / 捆绑 / 24h 成交任一项），补多少受 `ENRICH_POOL_MULTIPLE × gate_limit` 限制。答案落 `item.metrics`，但**不置 `enriched`、不写 `facts`** —— 安全判定仍只由 gate 那一步给。补齐走 `GmGn.fetch_chips`（只发 `token_stat` 一个请求），DexScreener 同批必问（市场口径源，发射台自报的深度不可靠）。 | 用全量 `fetch_token`，这一步就是「行数 × 0.45s 每主机节流」，worker 取 8 / 16 / 24 结果相同。 |
| 短名单排序键 ＝ 流动性降序，**完全相同**才用 24h 成交额破平。 | 反例：用 `min(流动性, 成交额)` 或以成交额为主键，深但无成交量的池会被刷量的浅池挤占。 |
| 淘汰数**按优先级累计，不是独立计数**；优先级顺序即设定页 `RULE_ROWS` 顺序（市值 → 流动性 → 持有人 → Top10 → 捆绑 → 貔貅 → 24h 成交 → 源码 → LP → 危险权限，距高回撤最后）。这是**归属顺序，不是运行顺序**。 | 各行独立计数，加起来就不等于 `dropped`。 |
| 距高回撤：回撤 ≤ `drawdown_max_pct` 淘汰，**三个读数任一跌够即淘汰**：源高点 `metrics.high_market_cap_usd`、库记录高点 `tokens.peak_market_cap_usd`（每轮回写、只升不降，所以源沉默的轮次也仍有真高点）、池面高点 `metrics.drawdown_pct`（GeckoTerminal 按池子全历史日线）。噪声闸 `HIGH_SANITY_MULTIPLE` 把超过链市值上限 ×50 的高点当解析噪声丢弃。**整源沉默 ＝ 放行，池面读失败 ＝ 未判定**（429 / 超时是未问到的问题，不是答案）。gate **不获取**池面读数（会触发 GeckoTerminal 限流），池面由画卡那一步一并取回，之后再判一次：跌破阈值即刻淘汰、依次补入下一个，所以卡片数不会因此变少。 | 反例：要求三个读数一致 → 169 个已跌够的币无一被淘汰，ARCAT 得以进入报告。 |

## 打分

分数是**池内百分位**，不是绝对阈值：每个因子先在本轮幸存者池里排名，再按权重合成。分母用哪个池子，决定分数的含义。

| 规则 | 说明 / 反例 |
| --- | --- |
| 分位分母 ＝ **本轮硬过滤幸存者**（不是全历史池，也不是过完安全门槛的池），中点法 `(below + 0.5*ties)/n`，用**补齐后的** `item.metrics` 构造（gate 之后建），让这个币和它比较的池子在同一口径上。 | 代价是**分母混口径** —— 被补齐的行是 DexScreener 市场口径，没被补齐的还是粗筛口径（见 `CLAUDE.md` · 边界与待决）。因此新源不应放进 `scan_sources` 以求「顺便校准」。 |
| 五个链上因子 ＋ 两个**逆向**因子：流动性 / 24h 成交 / 持有人 / Top10 / 捆绑，其中 Top10 与捆绑越小越好（分位反算）。 | 反例：把 Top10 / 捆绑按正向算，筹码越集中的币分越高。 |
| 综合分 ＝ 链上质量 ＋ 链下调研：两个总权重与两块各自的五个因子权重都在设定页（`config/chains/*.yaml`，以 `settings_versions` 为准）。 | 改一个就要把合计调回 100，否则 422。 |
| 链下调研没落地的标的 ＝ `pending`：本轮调研还没回来的既不参与排名也不显示 0 分，等它落地后下一轮才有分数。 | 若给 0 分，一个刚部署、调研尚未返回的币会被排到最后，与「未调研」混为一谈。 |

## 取值与合并

多源回答同一字段时以谁为准、什么算「答了」：判据是可信度与 `is not None`，不是到达顺序。

| 规则 | 说明 / 反例 |
| --- | --- |
| 同名标量的取值来源由 `DEFAULT_PRIORITY` 决定，字段级例外在 `FIELD_PRIORITY`。 | 反例：按「哪个源先回答」取值，源换了顺序结论就变。 |
| **0 是答案，不是缺失**：判空用 `is not None`；GMGN 的 `X or Y` 走 `_first(X, Y)`；dev 发币数 0 是一个发现。 | 反例：用 `if value:` 判空，0 被当作未答，dev 发币数 0 被丢弃。 |
| 集合类型的空值算「没答」：`collector.merge` 里 `[]` 不赢走字段。 | 否则 GMGN 的空 `pool_list` 会遮蔽 goplus 的结果。 |
| 覆盖方向是 `overlay(universe_bulk, per_token_merge)`：逐币富集值盖在批量视图上，**顺序不可写反**；`overlay` **不复制 `provenance`**，要单独合并。 | 顺序写反，粗筛行会覆盖刚付费取得的逐币值。 |
| 卡片读数取「先有值的那一份」：同一批读数库里存两份（`metrics` 批量榜单、`safety` 逐币判定），`cards._either` 逐字段取。 | 硬过滤与安检读的是 `metrics`，取错的后果仅是显示错误，但显示错误同样须修。 |
| 事实表只有一份实现：`report/facts.py` 的 `lines()` / `block()` / `safety_line()` 由**卡片与词条两处共用**，缺值输出「—」。 | 两边各拼一份，同一轮里两处对同一个字段的取值就不一样。 |
| 链接与社媒逐币从 DexScreener 读（`registry.ENRICH_ONLY`，在写词条之前，所以链接是写作输入的一部分）；取值只认 `baseToken.address` 命中的那一对，否则仅当答案里只有一条链时才接受。 | 反例：另一条链的 X 句柄写到这张卡上，比留空更糟。 |

## 读数与漏斗

面板上的四个数与淘汰份额只数一次，实现只有一个（**淘汰计数在 `core/funnel.py`，不在 `filters.py`**）。

| 规则 | 说明 / 反例 |
| --- | --- |
| 四个数（扫描 / 淘汰 / 候选 / 入选）**一次数出来**。 | 于是 `scanned = dropped + candidates` 是**恒等式**，不再是四个各自来源的数字碰巧排在一起。 |
| 落选池标题的「候选」**含入选**；`runs.dropped` 是总淘汰，份额单独列（`dropped_hard`，按优先级归属算出）。 | 前端用「总淘汰 − 其他」倒算，规则一改就错位。 |
| 落选池收**全部候选**：有分的按分数排，没分的排在其后并写明理由；退出项的名字从 `tokens`（CA 主档）取。 | 只收有分的，就会出现「候选 78」而表里只有 20 行。 |

## 缓存与记账

什么该进缓存，以及哪些请求进账本。

| 规则 | 说明 / 反例 |
| --- | --- |
| 「对方回答没有」同样是答案：生产者用 `http.NEGATIVE` 标记「对方答了，答案是空」，`cached` 会缓存它（读回来仍是 `None`）；真正超时 / 5xx 的 `None` 不缓存。 | 不缓存否定答案，Arc 上多数币在 GeckoTerminal 没有池，等于每轮重新查询，每次 3 次重试与 2.2s 节流。 |
| 记账要覆盖最贵的那台主机：`http.tally()` 是公开入口，`onchain.rpc_checked` 按同一套计数，所以链节点会出现在每轮的主机行里。 | 漏记链节点，每轮最慢的主机就不可见。 |
| 日志是唯一的耗时真相：handler 注册在 `crypto-hunter` 命名空间上（`CH_LOG_LEVEL`，页面「系统设置」可改、保存即生效），秒表由 `run_chain` 持有、按 `run(clock=...)` 传入。 | 不注册 handler，`logging.lastResort` 只写 WARNING 及以上，阶段耗时会被静默丢弃；数据库只留结论、不留耗时。 |
| 不应以单轮数字下结论：节点延迟轮间 2.2–4s 波动，`eth_getLogs` 的调用次数也轮间不可比。 | — |

## 读路径

链上直读这条路的调用清单与代价；这里的数字轮间不可比，不应以单轮读数下结论。

| 规则 | 说明 / 反例 |
| --- | --- |
| 单次上链请求有硬性下限（2–3s，与查询内容无关），并发几乎不增加成本，**批量省一次往返**。**一条链只有一个 RPC 端点，没有备份。** | 靠增加并发把链上阶段从 30s 压到 5s 做不到；说明效果时只引用轮间可比的请求数，不以单次 A/B 的耗时下结论。 |
| 提速只做「把本该同时问的一次问完」：`rpc_batch`、`nft_balances`、`contracts_of`、`_pool_logs` 的窗口并发、`decide.py` 的 `ENRICH_WORKERS`。 | 并发不保序会回包错位，所以回包按 id 映射回顺序。 |
| `eth_getLogs` 的调用次数**轮间不可比**：节点拒绝窗口宽度时对半递归，拒几个窗口由节点侧定。 | 查看整轮的 `ok=` 总数；波动全部来自节点。 |
| 30 次 / 轮里没有可删除的重复调用（一轮内不重复读同一个 CA）；要再压只能减少「哪些读是必需的」。 | **未改动，待定**（见 `CLAUDE.md` · 边界与待决）。 |

## 状态机

一轮只有一条状态链，终态落下之后不再改写；「正在跑」由执行器判定，不翻 `runs` 表。

| 规则 | 说明 / 反例 |
| --- | --- |
| 状态链 `pending → collected → scored → selected → written → researched`；任何在跑的状态都可以跳到 `cancelled` / `failed`；终态 ＝ `researched` / `cancelled` / `failed`。 | 在 `written` 之后再排一个异步阶段，报告已发布却还会被改写；把 `written` 也当终态，推送那一步没走完就停表。 |
| 落库那笔事务之前，任何阶段失败都可以重跑；之后不再改写。卡住的一轮靠**状态机上的重试与补发**恢复。 | 另写一个 watchdog 扫库改状态，等于两个写者争抢同一行。 |
| **「正在跑」由执行器判定，不翻 `runs` 表**：`schedule._live`（run id → 链 ＋ 配置）在 `submit` 时写入、future 完成时删掉；`busy_chains` / `live_configs` 只读它。 | 「任何非终态的行都算在跑」是有害的：进程中途终止会留一条永久非终态行，于是每条链永远有一轮在跑、ticker 再也不发轮（实测两条链都 busy，11 小时零个排期轮）。生产是一进程一端口，本进程的轮次就是全部真相。 |
| 开机收尾（`recover()`）：`pending` 重交，**其余非终态一律收尾** —— 存过 `reports` 的收成 `researched`，没存过的收成 `failed` 并写明原因；状态机不认识的旧状态直接写库收尾。 | 不收尾，页面就永远显示「正在运行」并持续走表。收尾只在开机跑一次、在任何 worker 之前。 |

## 进度与完成态

进度只增不减，各段额度按实测墙钟分配；进度条、运行面板与时间线键是三套粒度，不应混用。

| 规则 | 说明 / 反例 |
| --- | --- |
| 进度条只有五段（`progress.py` 的 `PHASES`，与根文件那九个时间线键是两套粒度（见 `CLAUDE.md` · 一轮流水线）），**五段不等长** —— 额度是两条链实测墙钟的加权占比，段内按**实际完成的工作量**填充；额度按阶段顺序排，所以进度条只会向前走。 | 按段均分会先停二十分钟再跳一格；改动阶段须同步修改下方额度表。 |
| 进度只增不减：`_set_progress` 落库用 `MAX(progress, ?)`。 | 段内额度是估的，回跳比推进缓慢更损害信任；`test_the_bar_never_walks_backwards` 守这一条。 |
| `sharpen` 与 `write` 不占额度、只记日志（每轮一行 `round <id> phase timings: ...`）。 | 数据库只留结论、不留耗时，日志是唯一能复核这些额度的地方。 |

| 进度段 | 额度 | 段内单位 |
| --- | --- | --- |
| `pull` | 0–19 | 每个扫描源拉完一次 |
| `topup` | 19–30 | 每补一个候选的链上数据 |
| `gate` | 30–51 | 每判完一个候选 |
| `draft` | 51–96 | 每调研并写完一个币的词条 |
| `score` | 96–100 | 一次 |

## 为什么这么定

每一条都是由一个具体的错误纠正出来的；现行口径见右列。

| 曾经的错 | 现在写在哪 |
| --- | --- |
| 距高回撤要求三个读数**一致**才淘汰 → 169 个已跌够的币一个没淘汰；库记录高点从不回写 → 那一半永远只是下界；池面读数读失败时静默放行而不是记未判定 | 本文件 · 硬过滤 |
| 短名单排序键曾用成交额 / `min(流动性, 成交额)` → 刷量的浅池把深池挤占 | 本文件 · 硬过滤 |
| DexScreener 的四个市场数在 `FIELD_PRIORITY` 里一个都没列 → 反复付费查询后又丢弃 | 本文件 · 硬过滤 ｜ `sources/README.md` · 数据源、安全判定与富集 |
| GMGN 榜单的 `volume` / `price_change_percent` 跟着查询窗口走，下游一律当 24h 记 → 5m 榜的 $47 被当成「一天成交 $47」淘汰 | 本文件 · 硬过滤 |
| 「空壳淘汰」与「零数据淘汰」共用一个 `missing_data` → 面板把每轮 85 条（Robinhood）/ 399 条（Arc）空壳行输出成「零数据淘汰」，而真正的零数据淘汰近 8 轮一次都没有 | 本文件 · 硬过滤 |
