## 1 定位

1.1 产品是加密圈的宏观信息流，承诺三件事：最新（覆盖率与时效优先于算法）、最火（热度）、可信（证据）。
1.2 形态：五个地方，分成两类。**实时视图**四页 —— 精选（过线的条目）、全部动态（窗口里的每一条，按天分组）、热点榜（条目聚成的事，按热度排）、主题（按「这条牵了谁」看，一个实体一栏），每次请求按当前窗口重算。**出过的刊**一处 —— 报刊一页，里面是日报（一天一期）/ 周报（周一到周日）/ 月报（一个自然月），读的是出刊那一刻的定稿。日报 / 周报 / 月报在左栏合成一行，版期由页内顶上的切换器选（4.5）。
1.3 读者：行业观察者，目前一人。选材口诀：这条会不会改变六个月后这个行业的格局。
1.4 语言：中文 + 英文。
1.5 与雷达的关系：两个产品、一套机器。雷达是微观（找低市值币），信息流是宏观（行业热点）。不合并，不共享流水线，前端也不复用雷达的卡片、设定与切换器。
1.6 蓝本：AIHOT（本地 D:/Code/AIHOT，MIT）。只仿骨架，不仿栈。

## 2 边界

2.1 不做行情型内容（价格自动成条）。行情数字只作证据，附在事件卡上。
2.2 本期不做：人工介入流程、定时调度、刷量对抗。
2.3 不碰雷达代码：`api/app/core/filters.py`、`core/scoring.py`、`core/funnel.py`、`api/app/sources/onchain.py`、`config/chains/*.yaml`。
2.4 `config/system.yaml` 只读复用（LLM、X 配置），不写入。
2.5 不引入 docker-compose、Postgres、任务队列。后端 Python、前端 TypeScript，沿用现有栈。

3.3 表和页面的关系：四个**实时视图**仍然每次请求重算（毫秒级），但条目不再现读源 —— 抓取那一路先把快照落 `feed_items`（8.1），视图读快照，写作站写下的中文字也从同一张表读回来（10.5）。快照与「算出来的东西」是两回事：热点、名次、窗口内的条数仍是每次重算，不落库。`feed_editions` 只由出刊那条路写，读方是三种刊（4.10）；出刊那条路要不要留，见第 7 节。

唯一一件落库的「算出来的东西」是**分组**：一件事由模型判过一次就写进 `feed_stories` / `feed_facts`，之后每个请求读它（11）。热度、名次、窗口内的条数仍然每次重算 —— 那些是每时每刻都在变的量，落库只会让它更旧。

3.4 出刊怎么发生。**调度已接**（2026-10-05）：`jobs.py` 的 `editions.publish` 每十分钟看一次，`config/feed/pipeline.yaml` 的 `schedule.<kind>`（北京时间，**留空 = 这一期不出**）到点就出。手动那条路仍在 —— `POST /feed/run?kind=` 出一期，`api/scripts/seed_editions.py` 往回填。回填能成立是因为 mock 的时间是相对写法（6.4）：把 `now` 挪到过去，读出来的就是"那一期的那一批"。相对那批在每一期里是一样的，所以往期不重样靠的是另一件事：fixture 里有 36 组**带日期**的归档条目（6.5），回填的 21 天、12 周、8 月各有一组属于自己的来源，热度压过公共池，于是 41 期的头条互不相同。

3.4.1 一期是一段**时期**，不是一次运行，这是这一节唯一要紧的事。`service.period(kind, moment)` 把时刻变成"10 月 3 日" / "2026-W40" / "2026-10"，id 由这个名字推出来（`feed-day-2026-10-03`）。于是"同一天跑两遍"不是靠谁记得去重，而是两次都算出同一个 id、撞上主键（`store/schema.sql`）。窗口两头都是 +08 的自然边界、半开，所以相邻两期严丝合缝，跨午夜的一条只会进一期。时段对齐还有一个好处：随手 POST 出来的时刻不影响它是哪一期，往期不会因此多出几行。

3.4.2 三种刊的窗口：日报 = 00:00 到次日 00:00（+08，下同），周报 = 周一 00:00 到下周一同刻，月报 = 1 日 00:00 到下月 1 日。周报按 ISO 走，周一是一周的第一天。

3.4.3 期末截止在**未来**（当天那期要到明天 00:00 才闭口），这是有意的：一期是一天，而一天不会在谁按下按钮的那一刻结束。窗口尾端之后的记录自然不存在，所以这不影响读到什么；它影响的是"这一期覆盖到哪一天"这句话能不能说准。

3.4.4 到点出的是**刚过去的那一期**。08:00 的日报讲昨天、周一的周报讲上周、1 日的月报讲上个月 —— 因为窗口是一个完整的日子 / 周 / 月，出刊那一刻那一期才刚开始，印出来是半张纸。上一期用「本期开始的前一秒」算，不用「此刻减一天」：进程停了一整天再起来，减一天还落回本期里，会印出一张刚开头半天的纸；减一秒永远落在刚过去那一期里。一轮十分钟，所以真正的时刻精度是十分钟。

3.4.5 出过的期**不再重出**：`feed_editions` 里已经有这一期就跳过。一期是出刊那一刻的定稿，重出会把它换成"现在这一秒的行情"，纸与详情之间那个刻意的差就没了。

3.5 信息流设定页（2026-10-05 落）。左栏 信息流 那五行下面的第六行，一个 Place 而不是 tab（8.3.10）：出刊节奏和两道闸门不属于上面任何一页。它和 系统设置 是同一套门面（8.9）—— `config/feed/pipeline.yaml` 是唯一真相，页面只是它的表，行 key 就是它在文件里的路径，PUT 回来的是文件现在的样子；页面不认任何键名。那一层**没有缓存**（每轮 tick 现读一次），所以改完下一轮就生效、不用重启。改了哪一行记一条 `settings.save`。

3.6 开销档位（2026-10-05 落）。四个站读的是同一份 `pipeline.llm()`，所以「一轮写作 40」从前是**每个站各读一遍**的 40（一轮上限 = 160 次逻辑调用）。档位把它收成一个下拉：`llm.preset` 取 `saver` / `standard` / `full`，表在 `pipeline.PRESETS`，页面上是「节省 / 标准 / 完整」。

| 档 | 预筛 | 结构 | 评分 | 摘要 | 理解 | 分组 | 综述 | 翻译 | 每天的逻辑调用 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 节省 | 0 | 0 | 0 | 0 | 关 | 关 | 关 | 本地 | ~1（只剩报刊） |
| 标准 | 0 | 1 | 0 | 1 | 关 | 开 | 开 | 本地 | ~900 |
| 完整 | 1 | 1 | 2 | 1 | 开 | 开 | 开 | 模型 | ~1600 |

数字按库里 ~270 条材料/天估；报刊是**一期一次**调用（`reports.py` 只有一处 `complete_json`），日报＋周报＋月报 ≈ 1.17 次/天。

**为什么是预设而不是八个开关。** 这些键互相牵着走：分组站的入口条件是 `db.feed_items_for_grouping` 的 `WHERE title_zh <> ''`，而中文标题是**写作站**写的 —— 关掉写作站，分组站一条也排不进来，热点榜退回 `events.group` 的规则分桶，综述站跟着没材料，最后报刊拿到的是规则版清单。八个开关各自看都对，合起来是一片空白，所以「哪几档配哪几档」定死在一张表里。

**键缺席按 `full`。** 一个自己传预算的调用点（测试、脚本）拿到的还是老行为；线上每一轮都带着 `preset`，走的才是页面上选的那一档。表外的值抛 `PipelineRefused`，不是安静地按某一档跑一整轮。

**两个「开不开」不是一回事。** `writing.enabled()` = 模型配好了、旋钮也开着（这一站能不能跑）；`writing.writes()` = 前者**而且**这一档真的写条目（节省档不写）。页面那一侧的门槛（10.10）读的是 `writes()` —— 读错一个，节省档下整页会安静地变空。报刊不看这两个：它一次一期，有模型就能写。

**翻译也是档位的一格。** `local` 走 `api/app/feed/localtranslate.py` 的 Argos（离线、CPU、不花钱），`llm` 走原来的 `translate-body` / `translate-post`。本地那条只认**纯文字**：块与小标题原样留着（`htmlbody.rewrite_html` 拼回去），块里行内的链接与代码换不回来。Argos 会把 `⟦0⟧` 与 `<a id="Ln">` 这些记号弄坏（实测 `⟦0⟧` 出来是 `QQ0⟧`），所以这一路**不能**走 `htmlbody.restore` 的对账，只能把译好的纯文字转义回写；译不动的块回 `None`，调用方拿原文顶上，与模型翻译失败时同一条路。

## 4 五个地方

4.1 一次读入，四个视图。四页都走 `views.collect(now, hours)`：读每个源 -> 去重 -> 切窗口 -> 学别名 -> 归组 -> 打标签与评分 -> 算热度。之后才分叉：

| 视图 | 窗口 | 门槛 | 形状 |
| --- | --- | --- | --- |
| 精选 | 72h | `score >= 65` | 按天分组的条目列表 ＋ 顶部「当前热点」前五 |
| 全部动态 | 72h | 无 | 同上，没有「当前热点」 |
| 热点榜 | 48h | `来源数 > 1 或 score >= 65` | 事件按热度排：No.01 大卡、No.02/03 并排、No.04-10 一行一条 |
| 主题 | 720h（30 天） | 无 | 左栏实体目录（分三组），中栏一个实体名下的条目按天分组，点一行进右栏 |

4.2 热度 = 来源数 x `0.5^(age/12h)`，年龄按事件的最后一条算。`value_at(event, when)` 是唯一算法，曲线、涨跌、指数都从它推。未来的时间戳在该时刻不计入 —— 所以那条线的最后一点必定等于它上面印着的数。
4.3 热度指数 = 热度 x 20，是印给读者的整数；条目上印的是「独立来源 4」这种计数与来源名，不是热度分。
4.4 页面不判：类别、标签、实体、分数、推荐理由、空态句子，以及 `热度指数` / `独立来源` / `一手` / `新` / `持平` 全部随 payload 下来（CLAUDE.md 2.3.3 / 2.3.4）。页面认识的只有版式标题：精选 / 全部动态 / 热点榜 / 主题 / 报刊 / 日报 / 周报 / 月报 / 当前热点 / 继续看 / 排名 / 报道 / 事件 / 正文。
4.5 四个实时视图共用一个壳（`FeedView.tsx`），但导航只在左栏，页内没有第二排 tab —— 同一件事两个入口，读者总会点到那个不生效的。唯一例外是报刊顶上那一排（日报 / 周报 / 月报，`DailyView.tsx` 的 `.daily-tabs`）：它换的是**版期**这一个参数，不是页面 —— 三种刊共用同一份版式，在导航里占三行等于说它们是三个地方（用户定的，2026-10-03）。它钉在档案栏顶上（往期列表比一屏长），换一种就换一个组件实例，于是选中的那一期跟着重来（4.10.1）。
4.6 页面上现在没有「跑一轮」：四个视图直接读源算出来。给一个纯读的页面配一个按钮，读者会以为不点它就没有内容。
4.7 两个详情页，形状是「列表行 ＋ 追加」：`item_detail` 是 `item_payload` 加副标题 / 导读 / 分段 / 原文 / 别家报道 / 时间 / 所属事件，`story_detail` 是 `story_payload` 加名次 / 小标签 / 综述 / 近 6 小时 / 时间线。按 id 取，不是让列表把那一行传下来 —— 详情页印的东西列表 payload 里没有，而「传下来」会让详情页依赖读者是从哪个列表点进来的，三个入口就长出三个形状。
4.8 详情不开新的一页：标题栏通栏，下面**平分两栏** —— 左半是列表，右半是详情（`.feed-pane`；用户定于 2026-10-03：「就是下方页面的一半」）。右栏**常驻**，没点开时就是空的，空的里面不写字。两栏各自滚（`#view-feed` 是 `height:100vh`，每栏 `overflow-y:auto`），所以在右边读着一条的时候滚左边找下一条，右栏不会跟着跑掉。右栏自带「返回」（后端的 `labels.back`）与 Esc，换一页（精选 / 全部动态 / 热点榜）自动收起。列表里的标题、热点榜的名次、时间线上的每一行，点开的都是我们的详情页（`<button>`，不再直接跳源）；源自己那一页是详情页里的「打开原文」按钮。左栏的滚动条不画（滚动照旧）；标题栏与「返回」栏下面那条线左右各留 16px，分类那一行下面没有线。窄到 1080 以下落回「右栏在列表下面」，那时整页恢复成跟着窗口滚。右栏记的是**一条路径**，不是一格：事件里点开一条报道，返回就回事件；报道里点「所属事件」，返回就回报导 —— 按钮上的字跟着上一级变（「返回事件」/「返回报道」）。左栏列表点开的是**起点**，整条路径换成这一条，返回恒为灰 —— 只有右栏里点出来的（「所属事件」、时间线里的一条）才压层；Esc 不往上走，是一路清空，换一页也清空整条路径。
4.9 窗口里没有的东西不画：没有别家报道就没有「另有 N 家信源报道」那一行，事件里只有它自己那一条也没有「所属事件」那一行。正文有几块就印几块（旧行的纯文本由 `analysis.normalised` 当场转成块），所以一句话的记录就是一页短的，不编三段出来；「摘要」与正文第一块在规则版下是同一段，页面不印两遍。

4.10 报刊（4.10.1 – 4.10.9）是出过的刊，不是第五个实时视图：那四页每次请求按当前窗口重算，这一页读的是**出过的刊**（`feed_editions`）—— 一期是快照，什么时候打开都是同一份，因为同一段时期跑第二遍还回库里那一行（`store/db.py` 的 `feed_edition_put`）。

4.10.1 三种刊是一个组件吃一个 `kind`（`DailyView.tsx` ＋ `daily.ts`），不是三份：它们差的只有一期的长短和几个词，而那些词（档号、分期、报头两行、点阵该亮哪几格）全部按 `kind` 分在 `daily.ts` 一处。版期由调用方 `FeedView` 持有（`kind` 初值是日报），所以从报刊切走再回来，看到的还是上次那一种。加第四种刊（比如季报）要动的是 `service.KINDS`、`daily.ts` 的一个分支和 `DailyView.tsx` 那排里的一个按钮 —— 不再动 `Rail.tsx`。

4.10.2 版式是三栏：一栏档案（340，放得下 15px 的标题；280 时一行只剩十三个字）、中间一张纸、右边点开的那一件事。纸比详情宽（3:2）—— 报头是「刊头 ＋ 报眼 ＋ 指标条」一整块，均分给纸的宽度不够，而详情那一栏 320 上下就读得动（用户定于 2026-10-03）。窄到 1080 以下收成一栏，顺序是档案 -> 纸 -> 详情，档案栏在那时变成一块自己滚的短栏（不给高度上限，几十期往期会把纸顶到几千像素以下）。

4.10.3 左栏是**档案**：一期一行，左边一个大字（日报是几号，周报是第几周，月报是几月），右边小字（日报星期几，周报"09.28 起"）加一期的标题。标题是后端给的（`reports.headline`）—— 页面要印它就得把正文打开，而列表的用意正是不打开正文（3.2 的"不印 payload"）。分期：日报按月，周报和月报按年；再细一层就不是"翻旧报纸"，是"查档案"。

4.10.4 报头是"刊头 ＋ 报眼 ＋ 指标条"一整块，底下一条粗线，线以下才是版面。刊头是大字 ＋ 两行（`2026 年 10 月` / `星期六`）。报眼是期号 ＋ 一格一期的点阵：日报按它那一期所在的月份排成日历的样子（按星期对齐，因为读者认的是"上周三"），周报是全年 53 格，月报是全年 12 格；点阵亮着的格子就是出过刊的那些。点阵下面那句数（"本月 3 期"）只在**这一组期数完整**时才印 —— 列表只加载最近 60 期，被截断的一组数出来的数会少，而一个可能说错的数比没有数更糟。

4.10.5 期号由后端**数出来**（`store/db.py` 的 `_ISSUE_NUMBER`：同一份档案里不比这一期晚的那些有几期），不是存下来的。存下来的那份在每次回填之后都要全部重算，而"从最早的往回填"和"从今天往前填"算出来的号不一样 —— 一份取决于写入顺序的"第几期"会在下一次回填时自相矛盾。

4.10.6 报头那几个数（`reports.metrics`）**词和数一起从后端来**：`8 件大事 / 12 个来源 / 38 条动态 / 3 分钟读完`。上一版这里印的是页面自己编的"读了 N 条"，而"个来源"它编不出来 —— 那几个数只有后端算得出（`sources` 是按 `source_id` 去重之后的独立来源数，见 `heat.py`）。值为 0 的那几项不印，空的一期整页就一句话。

4.10.7 相邻期在纸的页脚：左"上一期 · 9 月 25 日"，右"下一期 · 9 月 27 日"，名字里带日期，按下去之前就知道会落在哪。最边上的两期没有邻居，那一边就不出现。版式那一条见 4.10.2 —— 三栏、纸比详情宽，是跳出 4.8 那条房规的（用户定于 2026-10-03）。

4.10.8 纸上的每一行字点开的都是**我们自己的事件页**，不是原文（用户定于 2026-10-03）：头条那行大字可点，今日看点的每一行也可点，全是同一个动作。原文那个出口留在事件页底下的「打开原文」。于是纸和详情会**对不上** —— 纸印的是出刊那一刻的来源数与热度，详情是现在这一秒重算的。这个差是有意留的：一期是那段时期的定稿，详情是行情，两处各印各的读数，而读者要的正是这个差。

4.10.9 右边那一栏不是为报刊新写的：它和四个实时视图的右栏是同一个组件（`FeedView.tsx` 的 `Pane`），返回 / Esc / 压层 / 常驻的规矩一处都不用重写。纸上的行算**起点**（整条路径换成这一条，返回恒灰），和榜单、列表上的行同一个规矩；只有栏里点出来的（事件里的某条报道、报道的「所属事件」）才压层。换一种刊（日报 -> 周报）也清空这条路径 —— 栏里开着的那件事是上一份报纸上的，而纸已经换成另一期了。

4.11 主题（4.11.1 – 4.11.5）是四个实时视图里的最后一个，但它问的问题和另外三个不同：另外三个按「这条东西是什么」看（类别、过没过线、热不热），主题按「这条东西牵了谁」看。这里的词是**实体** —— Ethereum、Binance、SEC 这种名字 —— 一条可以牵好几个，也可以一个都不牵，所以它回答的是「这条线最近动了没有」。它**不按赛道分组**：赛道和精选那条类别栏是同一件事，多一份只是把同一批条目换个名字再列一遍（用户定于 2026-10-03）。

4.11.1 版式三栏，跟着报刊走（`TopicsView.tsx` 出前两栏，第三栏是四个实时视图共用的那个 `Pane`，4.8）：左栏目录 260，中间是选中那条线的内容，右边是点开的详情。三栏的顺序与报刊一样，最宽的那一栏不一样 —— 报刊把 3fr 给纸（版面要宽度），主题把 3fr 给中栏（正文要宽度），所以 `topics-body` 与报刊同名不同序。中栏的每一行算**起点**，和榜单、列表上的行同一个规矩（整条路径换成这一条）；只有右栏里点出来的才压层，返回 / Esc 的规矩一处不用重写。窄到 1080 以下收成一栏，顺序是目录 -> 正文 -> 详情。

4.11.2 窗口是 30 天（`views.TOPIC_HOURS = 720`），比全部动态的 72 小时长得多，这是有意的：全部动态看「现在在发生什么」，主题看「这条线还在不在」—— 一条线几天只出一条也算它还活着，压进 72 小时里大半的线都会空，而一页大半是空的目录等于没有目录。窗口长短只在后端一处，页面印的是后端发的 `window_days`，自己不写死 30（CLAUDE.md 2.3.3）。

4.11.3 左栏的条数与中栏那一批走同一套窗口与同一套算法（两处各自 `collect(now, TOPIC_HOURS)`），所以对得上；中栏顶上那个数直接用后端回的 `shown`，不自己数一遍 —— 页面数出来的数和后端给的数迟早会差一条。这个数只在**这条线**上出现，不印「近 30 天一共多少条」：那是全部动态要回答的。

4.11.4 一条空线（窗口里一条都没有）画出来但点不动。藏掉的话读者不知道这条线存在，只是现在没东西 —— 而「现在没动静」正是这一页要回答的。词表之外的名字（读者拿着更早一份词表点出来的）回一个空窗口，不是 404：页面上「这条线现在没东西」和「这条线不存在」长得一样，不值得让 404 去区分它们。

4.11.5 实体名录是 `taxonomy.ENTITY_TAGS`（24 个），左栏那三组（链与协议 / 交易所 / 机构与监管）只是**摆放**，写在 `taxonomy.ENTITY_GROUPS` 一处；分组不改匹配、不改卡片角标，只在页面上分个段落。分组里的名字要与名录严丝合缝 —— 打错的那个实体会静默地不上墙（没有第二处会报错），所以有一条测试盯着「分组里的每个名字都在名录里、名录里每个名字都被分组覆盖」。

4.12 列表那一页的一条是一个**块**（4.12.1 – 4.12.6）。这是版式，不是判断：谁算精选仍然是后端的 `score`，页面只决定这些东西怎么排（4.4）。形状和密度参考了 AIHOT 的精选，颜色、方块与动效全部是这一套自己的 —— 全站没有圆角卡片，也没有 hover 抬起。

4.12.1 一条 = 时刻 ＋ 竖线 ＋ 一块：左边时刻（tabular-nums），中间一条 1px 竖线，一段配一张卡片：上下两端齐卡片方框的上下边框，和左边框之间留 8px（齐的是上下，不是左右），右边一块 `--surface` 加 1px `--border` 的方块。悬停只把边框换成 `--accent-tint`，不位移、不加影子 —— 影子和大圆角是别处的语言，引进来这一页就跟全站不是一套了。

4.12.2 一天一个头：日期、折叠箭头、星期、条数。箭头折的是这一天，不是页面。一天几十条的时候，读者要的是"今天看到哪了"，不是把昨天也滚一遍。

4.12.3 分数按档上色，**只上色不换数**：80 以上 `--ok-fg`，65 以上 `--accent-fg`，再低 `--fg-2`。档位是版式，谁过线仍然是后端的 `score`。所以精选页上只会看到前两档，第三档出现在全部动态里。

4.12.4 图与「另有 N 家信源报道」随行下来（`item_payload` 的 `media` / `other_reports` / `other_report_count`），不留给页面去查：图是来源自己带的（只有 X 这类会带）；折叠行是同一件事里别家的报道（`views.other_reports`，按发布新到旧、每**家**只留最新一条，这一条自己的来源不算 —— 它已经印在卡片顶上了）。计数是**信源家数**而不是列表长度 —— 列表截断到 `OTHER_REPORTS_LIMIT` 条，拿长度去印会在截断之后撒谎。图挂掉就自己收掉：一块破图占着位置比没有图更糟，而这张图本来就不是这一条的主要内容。两样都可以没有，大多数条目两样都没有。

4.12.5 「当前热点」是一块底，不是一段没有边界的文字：它是榜的头部，不是今天的一条，所以和下面每一条同一个方块。名次前三用全站那一套三色（`--podium-1/2/3`，和报告页名次同一个来源），右上角「完整榜单」是它和热点榜之间唯一的门 —— 少了它，想看第六名的读者没有地方可去（换页由 `App` 递下来的 `onOpenBoard` 做，壳不自己认页签）。

4.12.6 读过的一条标题淡下去（`--muted`），悬停仍然给回链接色（淡是状态，不是这条不能点）。已读记在本地（`web/src/features/feed/read.ts`，只留最近 400 条）：它管的是"我看过这行没有"，是浏览器的事实，不该为它多一条写请求。

2. 公开范围在读取时判定：不接受时改状态，所以撤回几分钟内生效。
3. 事件两级模型：fact（同一次发生）与 story（含后续进展）；推送按 fact 去重，热度按 story 算。

## 6 mock 的边界

6.1 mock 只替采集层，即一条原始发现记录，字段至少：来源类型、来源标识、原始 ID、标题或正文、原文链接、发布时间、作者、自带的图（`media`，只有 X 这类会带）。
6.2 不要 mock 成品卡、成品刊。身份判定和「算不算今天」是先后两道闸门；mock 成品会把这两道绕过去，而后面所有东西（归组、热度、去重、撤回）都架在它们上面。
6.3 mock 要满足「今天的真形状」：同一件事有多个来源，有首发有转载，发布时间有差，有跨天。
6.4 实现：`sources/mock.py` + `mock/records.json`，286 条 / 31 个来源。其中 106 条是**相对时间**（支持 `-2h` 这类写法，所以这一批不会过期），跨 4 天、含 21 个多源事件簇、32 条带正文。另有意留 2 条重复，给去重测试用。其中 6 条 X 记录带图，图是 `web/public/feed-media/` 下三张本地 SVG：mock 的图不该指着外网 —— 外网一挂这一页就少一块，而这件事跟信息流本身没关系。带正文的记录各有两段（段落之间空行），所以详情页的「正文」有东西可画、`analysis.article` 的位置小标题也真的用得上；剩下那些只有一句话的记录仍然只有一句话 —— 那就是一页短的，不编。

6.5 另外 180 条是**带日期**的归档条目：36 组、每组 5 家来源，发布时间钉在某一天的 17:30–18:30（+08）。这个时刻是照着回填锚点选的 —— `seed_editions._at` 用 12:00 UTC，也就是 +08 的 20:00，所以每期的头条都落在锚点前一两小时里，热度压过公共池。回填的 21 天、12 周、8 月各分到一组，41 期的头条于是没有两期相同。代价写在这里：这批条目只在所属那一期里当头条；落在 72 小时窗口内的那 15 条（最近三天各一组）会同时出现在实时流里，窗口之外的则不出现 —— 今天的头版本来就该出现在今天的实时流。"所有内容都不过期"这句话从此只对上面那 106 条成立。

## 8 接真实源与 LLM：已定的三件（2026-10-04）

8.1 **采集一次，四个视图读同一份。** `views.collect(now, hours)` 现在在每个请求里现读全部源，打开一条详情页（`views.find_item`）还会再读一遍 —— 吃 mock 是本地一份 JSON，没事；接上三十二个源之后，每个请求就是几十次网络往返。所以真实源落地**之前**先插一层快照，快照落 `feed_items`：表与 `feed_items_put` / `feed_items_for` 已经备好并测过（生产一次没调用），一张表同时当缓存与账本，比「内存 TTL 再另存一份刊」少一个概念。窗口按视图不同（72h / 48h / 720h），所以快照留 30 天。

快照里的 `published_at` 一律归一成 **UTC、秒精度**再入库：SQL 比的是字典序，而
`2026-10-03T00:00:00+00:00` 与 `2026-10-03T00:00:00+08:00` 是墙上差八小时的同一对时刻，

8.4 **源是数据，抓法只有四种。** 一个源不是一段代码，是 `feed_sources` 表里的一行：`id` / `name` / `kind` / `config`（JSON）/ `tier` / `first_party` / `participation_mode` / `interval_minutes` / `enabled`，运行态另加 `cursor` / `fail_count` / `health` / `last_error` / `last_fetch_at` / `last_ok_at` / `next_fetch_at`。`kind` 只有四种，一个 kind 一个通用抓取器 —— 选择器和字段路径全写在那一行的 config 里：

| kind | 抓取器做什么 | 喂给谁 |
| --- | --- | --- |
| `rss` | 读一份 feed；ETag / Last-Modified 走 304 | 英文媒体 7 ＋ 中文媒体 4 ＋ 监管 2 ＋ 官方博客与交易所里能出 feed 的 4 家 |
| `json_list` | 读一个 JSON 接口，字段路径写在 config 里 | Binance 公告 |
| `web_list` | 按链接里的字串挑出文章链接（`linkContains` / `linkPrefix`），`baseUrl` 把相对链接补全；**不装 CSS 选择器引擎** | 链捕手、深潮、Circle |
| `x_search` | 包 `search/engines/xsearch.py` | X 23 个账号 |

于是加一个源只加一行数据：不写函数，不动 `sources/__init__.py` 的 `ALL`。`sources/registry.py` 那 32 个常量改成 `config/feed/sources.yaml` 出厂清单（导入到表），运行态只写表、不回头写文件。config 的键按 kind 走白名单，**不认的键让这一轮失败**，不静默落回通用解析 —— 雷达那边 `pipeline.scoring.product_weight` / `unlisted_policy` 两个键从来没生效过，就是这个毛病。

8.5 **每个源一本账。** 没有这本账，接上真实源只是把「不吐条目」这件事藏得更深。

| 事 | 规矩 |
| --- | --- |
| 失败 | `fail_count` ＋1；1–4 次记 `degraded`，≥5 次记 `failing`；**失败的抓取不推进 `cursor`**，不然那批数据永久丢 |
| 退避 | `next_fetch_at = now + min(interval_minutes × (fail_count + 2), 360 分钟)` |
| 付费失败 | 不涨 `fail_count` —— 不是源的错，不该让它背 |
| RSS | 用 ETag / Last-Modified；**首次导入不存校验器**，否则第二轮直接吃 304，白空一次窗口 |
| 去重 | 放在补细节页**之前**，且用和入库同一个 identityKey（不然 URL 别名既多买一次细节页，又把别的文章挤出窗口） |
| 首次导入 | 有界（30 条 / 12 个月），标 `backfill`，归档不推送 —— `blog:ethereum` 实测 641 条，不设限会一次灌满 |
| 标题不成句 | **已落**（`sources/detail.py` 的 `looks_like_title`）：长度 > 100 字或等于「阅读全文 / 了解更多 / Read more」→ 这不是标题，去细节页取真的，取到就换掉 |
| 细节页 | **已落**（`sources/detail.py` ＋ `sources/collect.py` 的 `_fill_details`）：只给「缺正文」或「标题不是标题」的条目抓，每轮有预算（`config/feed/pipeline.yaml` 的 `detail.maxFetches`）；预算用不完就接着补以前欠下的，否则被截断的那批永远等不到下一轮。失败的也记时刻（`feed_items.detail_at`），`retryHours` 之内不再敲 —— 坏链接每轮都敲会把好条目的位置占掉 |
| 每轮记账 | 每次抓取落一行 run（源、起止、found / created、错误）。`found = 0` 就是坏了 —— HTML 源的选择器失效不报错，只是从此不吐条目，这是最坏的失败方式 |

8.6 **频率与调度。** 每个源一个 `interval_minutes`，按「这个源多久才出一条」定，不按重要性定 —— 官方博客再重要也是两小时看一次，因为它两小时就是没有新东西。

| 源 | 间隔 | 为什么 |
| --- | --- | --- |
| 交易所公告（Binance / Kraken / OKX） | 15 分钟 | 上币公告是分钟级时效，慢一小时这条就废了 |
| RSS 媒体 7 家 ＋ 中文媒体 4 家 | 30 分钟 | 一天几十条，够密 |
| 监管（SEC / CFTC） | 60 分钟 | 一天几篇，晚一小时零损失，但绝不能不抓 |
| 官方博客 | 120 分钟 | 同上，它本来就不常发 |
| X 11 个账号 | **120 分钟** | 最贵的一档，先按两小时跑，量到会话能扛多少再收紧 |

调度走**进程内后台 tick**：进程起来时挂一个 asyncio 任务，每分钟挑 `next_fetch_at <= now()` 的源（从没抓过的优先，一次一批），入队先把它推到 `now + 10 分钟` 占位，抓完写回真值。不引队列、不加进程。重启不丢：`next_fetch_at` 在表里，自己接得上。手动的 `POST /feed/run` 保留。

自适应重算（每天按近 7 天 `perDay` 反推 `1440 / (perDay × 3)`，夹在 15–60 分钟之间）**第一版不上**：现在还没有 `perDay`，公式没有输入。先手填上面那张表，跑出数据再说 —— 那句「每次去看应该刚好有 3 条新的」是它的意思，留着当目标。

**这一批落到哪儿了（2026-10-04）：** 8.1 的快照层在 `sources/snapshot.py`（四个视图与三种刊读
的都是 `feed_items`），8.2 的清单在 `config/feed/sources.yaml`，8.4 的四种抓法在
`sources/kind/`，8.5 的账在 `sources/collect.py` ＋ `feed_sources` / `feed_fetch_runs`，8.6 的
时钟在 `sources/tick.py`（起进程时导清单，之后每分钟一班）。真实网络实测：6 个 RSS 源 15.7 秒
抓回 263 条、`x:coindesk` 5.1 秒 20 条，两轮都 0 失败。首轮连跑 45 个源，红了七行（见下）。

## 9 LLM 接入：入库时对全部条目跑（2026-10-04 定）

9.1 **时机定在「快照入库」这一站，范围是全部条目，不设精选门槛。** 8.3 那版是「只给过 65 分的条目」，现在改掉：模型当前免费，门槛的唯一作用 —— 省钱 —— 不存在了，而「入库时」是唯一能保证页面随开随有的时机：读者打开任何一条（包括没人点过的冷门），写好的标题与摘要已经在库里，不必等、不必懒加载。代价是抓取循环里多一段模型调用，见 9.5。

9.2 **先补正文，再写。**（已落：`sources/detail.py` ＋ `config/feed/pipeline.yaml`，2026-10-04。
真机首轮实测：欠正文的 654 条里，`web_list` 61 条几乎全补上（链捕手 25/30、深潮 28/28、Circle 3/3），
`rss:theblock` 那 19 条靠浏览器通道补上（普通 GET 一律 403）；没补上的里 `exchange:binance` 20 条是
WAF（`HTTP 202`，浏览器通道也一样），其余是零散的 404 与超时，下一趟还会再来。） 现在库里 62% 的条目没有可用正文：`web_list` 61 条与 `json_list` 20 条**全空**，`rss` 769 条里只有 196 条够 200 字。没有正文时模型能写的和规则版（`analysis.py` 取第一段）没区别 —— 所以 `detail.maxFetches`（8.5 里一直没做的那格）是这一步的前置：按预算对条目抓详情页、补进 `body`，再交给模型。顺序反了就是白花钱。

9.3 **模型写什么。** 两档、两次调用（为什么不是一次：10.2）。**理解档**对全部条目写中文标题 + 摘要 + 推荐理由；**翻译档**只对过了精选线、而且真有正文的条目写导读 + 逐段译文。材料不足的条目走「材料不足版」提示词，不硬编内容。

| 字段 | 现在（规则版） | 入库时（模型） |
| --- | --- | --- |
| `title` | 源自己的写法（英文也是英文） | 理解档写中文标题（`title_zh`），源的那条留着给「原文」 |
| `reason` | 按分类套一句模板，同分类的条目一模一样 | 写这条为什么值得看 |
| `summary` | 正文第一块 | 理解档写一句摘要（80-160 字、最多三句，照 AIHOT） |
| 正文 | 源给的 HTML，行内标签、脚本与样式混在一起 | 采集时压成**块级 HTML**（`htmlbody.sanitize`，块内保留行内标签），翻译档先把链接/代码换成占位记号再按块换字进 `body_zh`，见 10.9 / 31 |
| `subtitle` | 正文第一句 | **删掉这一格** —— 它和摘要说的是同一件事，而模型的摘要写得更好 |
| `category` / `tags` / `entities` | `taxonomy.classify` 关键词表 | 第二步再换模型 |
| 事件 `digest` | 最新三家各说一句 | 一段综述 |
| 一期 `headline` / `metrics` | 排第一那条的标题 | 一期一次 |

源给的 `title` 一个字都不动：中文标题进 `feed_items.title_zh`，页面印哪个由 `Item.display_title` 一处决定（`title_zh or discovery.title`），源的那条随行给 `title_original`，两者不同时详情页多印一行灰字原文标题。「中文 / 原文」那个开关管的是**正文**，见 10.8。

9.4 **不交模型的两件。** `score` 与精选门槛留在代码里 —— 输入是数字、权重是产品决策，模型给分只会让口径漂（AIHOT 同样把门槛写在 `industry/selection.ts`）。去重、窗口、排序、刊期边界同理。

9.5 **入库时跑的三条约束。**
- **不阻塞抓取**：一轮 `poll()` 会一次带进几十条，模型调用要并发有上限、单条有超时，超时就放手。
- **失败必留痕、必可补**：规则版结果**先落库**，模型成功再覆盖，并记下它是谁写的（`rule` / `llm` + 提示词版本）；模型失败或没配，页面照旧有东西可画，这些条目可重跑。模型挂了不能把整条流水线染红。
- **限流要认**：免费模型一样有每分钟上限。`llm_calls`（已有）只是账本，熔断已落（10.4）—— 限流时收手，不把一批条目写成半截。

9.6 **记账与提示词。** 复用 `llm.complete_json(purpose=..., prompt_version=...)`，purpose 起 `feed.*` 前缀（如 `feed.understand`），与雷达的 `research` 分开看。提示词放 `api/app/feed/prompts/*.md`，**版本取内容哈希**：位置照 `api/app/report/prompts/research.md`，但别学它手改 `research.md@8` —— 人会忘。

9.7 **这一版不做的。** 预筛（我们的源全是加密，没有「是不是本行业」这个问题）；校准样本集（门槛与提示词先靠人工看错例，条目量够再建）；雷达那边的 LLM 一律不碰。

## 10 写作站：两档、三态、熔断（2026-10-04 落）

10.1 **落点。** 编排在 `api/app/feed/writing.py`，提示词 `prompts/understand.md` 与 `prompts/translate-body.md`，接线在 `sources/collect.py` 的 `poll()` 末尾 —— 排在补正文**之后**：摘要是对正文的摘要，而正文常常是这一轮才补上的（列表页只给链接），顺序反了就要等下一轮才有人读它。预算在 `config/feed/pipeline.yaml` 的 `llm:`（`maxItems` / `concurrency` / `timeoutSeconds` / `retryHours` / `maxFailures`），`maxItems: 0` 就是整个写作站关掉。**哪几档真的跑由档位定**（`llm.preset`，见 3.6）：标准档只跑结构＋摘要，评分与理解档不跑；`writing.enabled()` = 旋钮开着 **而且** 模型真配好了，`writing.writes()` 再叠一层「这一档真的写条目」，发布门槛（10.10）读的是后者。

10.2 **为什么两档，不是一次调用。** 译全文比写一句话贵一个量级，而没进精选的条目不会有人展开读它的正文。理解档对**全部**条目跑（9.1），翻译档只对过线的跑。

| 档 | 谁进 | 一次调用写 | 落库的列 |
| --- | --- | --- | --- |
| 理解 | 全部条目 | `title_zh` / `summary` / `reason` | `title_zh` `summary_llm` `reason_llm` |
| 翻译 | 过了精选线 **且** 原文不是中文 **且** 真有块 | 逐块译文 `t` | `body_zh` / `body_complete` |

- 「有正文」判的是**块数**，不是「字够不够多」：只有一块长正文（推文、一句话公告）也该译。正文与标题一字不差的那种 = 没有正文，不译。
- **中文源不译**：先信源自己的声明（`feed_sources.language` 写着 `zh` / `en`），声明缺席才去数正文前 400 字里的汉字（`writing.zh_source`）—— X 那种几十字的帖子，数不出汉字说明不了什么。
- 块数必须与输入**完全相同**：多一块、少一块、合一块都拒收（`TranslateDraft` 只有 `t: list[str]`，块数对不上就作废）。块是原文的形状，模型的活是译它，不是重排它。
- **按块分批问**（`BATCH_CHARS = 3500`）：一批的答案对不上就把这批**对半重问**，对的那一半照样收下（AIHOT 只在对半两边都对上时才要，我们多收一半 —— 已经花掉的往返不该白花）。

10.3 **三态 `llm_stage`。** `NULL` = 一个字都没写；`understand` = 理解档写完、翻译档欠着；`full` = 这一条该由模型写的都写完了。这一列由**行自己**说，不由调用方记 —— 所以「上一轮翻译失败了」不需要任何额外状态，下一轮它从翻译那一档接着走。补丁是**一串**而不是一个：理解档成功、翻译档失败时前者照写（两档写的是不同的列），把两个答案捆成一个就是"失败一次等于把上一档白写一遍"。没有正文、原文是中文、或没过线的条目也记 `full` —— 它该由模型写的部分确实写完了，而不是因为它译过了。没译完的**留半篇**：译上的块换中文，没译上的块留原文，`body_complete = 0`，`llm_stage` 停在 `understand`，过 `retryHours` 再来补缺的块。

10.4 **熔断与重试。** 一轮里**连着**失败到 `maxFailures` 就收手；闸门在批与批之间，一批里最坏多浪费 `concurrency` 次调用。已经问过又失败的行记了 `llm_at` → 推到 `retryHours` 之后；**没轮到**的行 `llm_at` 还是空的 → 下一轮排在最前（`feed_items_pending_llm` 把 NULL 排在前面）。日志与 `report["wrote"]` 只数**真的写上了字**的那些：失败补丁只带一个 `llm_at`，数进 `wrote` 会让日志说这一轮写了四十条，而页面上一个字都没变。

10.5 **字怎么到页面上。** 库是唯一落点：入库那一刻写一次，之后每个请求读同一份（`snapshot.read_written_window` → `writing.overlay`，在 `views.collect` 里、`heat.annotate` **之后**）。顺序不能反 —— 反了规则版会把模型写的字整个盖掉，而那一趟每个请求都要走。`apply_item` 只盖模型真的写过的格：空着的那几格保持规则版，因为规则版至少是原文自己的话，而一个空串会让页面印出一块空白；`title_zh` 是例外，它空着的意思正是"印源自己的标题"。事件的名字跟着代表性那条的中文标题走，否则热点榜是英文、点进去是中文。

10.6 **提示词版本取内容哈希**（两串都随文件内容变，当前值看库里 `feed_items.prompt_version`），不手写序号；两档都用了就记两串。理由见 9.6。改一句提示词，版本就换一个 —— 库里那一列说的是这一条**当时**由哪一版写的。

10.7 **不交模型的。** `score`、精选门槛、去重、窗口、排序、刊期边界（9.4）；正文怎么分块、怎么净化也不交（9.3）—— 那是采集层的事，模型只负责换字。

10.8 **页面上那几个说法。** 摘要那一格有两个名字：`summary` = 「摘要」（规则版取正文第一块）、`summary_ai` = 「AI 导读」（模型写的），由 `written` 选一个 —— 把规则版印在叫「AI 导读」的地方就是一句谎话，所以两个说法都由后端给（CLAUDE.md 2.3.3）。正文那一栏：`body` = 「正文」、`body_zh` = 「正文 · AI 翻译」、`body_src` = 「正文 · 原文」，没译完时多一句 `body_incomplete` 提示去看原文。标题那一行的规矩照 AIHOT：模型写的中文标题与源自己那条**不同**时才在标题底下多印一行灰字原文标题，X 帖不印（源标题就是那条推文本身）。中文/原文开关**只在 `body_zh` 有值时才给**（`translated` = 「中文」、`original` = 「原文」），所以中文源与没过线的条目都没有这个开关。

10.9 **正文是块，不是段落数组。** 采集层把源 HTML 压成**块级 HTML**（`htmlbody.sanitize`：块 = `p` / `h1`-`h6`（并档到 `h5`）/ `li` / `blockquote` / `figcaption` / `pre` / `figure` / `td` / `th` / `caption` / `dt` / `dd`；块内**保留行内标签** `a` / `code` / `strong` / `em` / `b` / `i` / `u` / `s` / `del` / `sup` / `sub` / `mark` / `span`，和 AIHOT 的 `ALLOWED_TAGS` 同口径），`feed_items.body` 存的就是这个串，翻译按 `blocks` 切开、`rewrite_html` 换字。整棵丢掉的是：促销 class（`msr-promo`）、1px 像素、`lib/image-url.ts` 那批广告同步域（见 31）。旧行是纯文本，`analysis.normalised` 在**读**的时候把它当块，所以不用回填老数据。

10.10 **写完才发（AIHOT 的门槛）。** `views.collect` 里写作站开着时只留**已经写过中文标题与摘要**的条目（`read_written_window`）—— 一条要么有中文标题与摘要，要么不出现在页面上，页面不混着中英两种半成品。写作站关掉（没配模型、`maxItems: 0`、或者这一档根本不写条目 —— 节省档，三种都算）门槛跟着关掉，否则开发机上信息流会安静地变成空页 —— 所以问的是 `writing.writes()` 而不是 `enabled()`（3.6）。要让一批旧行重译，得先把它们的 `llm_stage` 退回 `understand` 并清掉 `body_zh`，否则它们会带着旧字过关。

10.11 **推文那一档另算。** X 帖的正文就是那条推文本身，所以它**整条当一块**问 `prompts/translate-post.md`（要求保留 `@` / `#` / 网址 / 换行，只译主推文），不是按块分批；挖掉网址后不到 60 字的**短帖不译** —— 短推的意思已经由中文标题与摘要承载（AIHOT 的 `X_MIN_CHARS`）。引用推文既不进正文也不单独译，它只作为一段背景进理解档的材料，`summary` 要把它的关键点整合进去（AIHOT 的 `summarize-*-quoted`）；取它的是 `search/engines/xsearch.py` 的 `quotedTweet`，落在 `feed_items.quoted_json`。
## 11 分组站：事实与事件（2026-10-05 落）

11.1 **为什么分两层。** 热点榜数的是「几家在说**这一次发生**」，时间线要的是「这件事先后发生过什么」。
一张表存不下两个问题：把新进展也钉在同一个事实上，同一家会被数两次，热度就成了「发了几条」而不是
「几家在说」。所以三张表 —— `feed_stories`（一件事）、`feed_facts`（这件事下面的一次发生）、
`feed_item_facts`（一条报道落在哪个事实上）。`role` = `primary` 是这次发生本身，`report` 是又一次
报道；`root` 只标这件事的**根**事实（最早那一次发生），后续只挂根：一条已经有后续的事实不再收新的
后续，否则时间线会长成一条链，两年前的事能挂到今天（AIHOT 的 `storyRoot`）。

11.2 **判定在 `grouping.py`，读写在这里。** 四步，顺序固定，换一种会改变结果：

    召回   过去 14 天的事实，取最像的十条       字符二元组重合（线 0.25）兜底；有向量之后是余弦（线 0.6）
    判定   逐条问模型这一次是什么关系           四类，各带置信度，答案按 C1/C2 拨回候选
    复核   召回分不到 0.85 却说是「同一次发生」  再问一遍（purpose = `feed.group_review`）
    定夺   先报进那个事实；再到后续进展；盘点不合并；其余自己起一件事

`boost` 是材料里就写着的关系 —— 同一个网址、或者这条推引用/回复的那条 —— 直接进候选，不让模型去猜。
常量与 AIHOT 的 `events/group.ts` 同值（0.6 / 0.85 / 0.8 / 0.75）。

11.3 **排队与顺序。** `stories.run` 只收「写作站写过中文标题、还没归过组」的行，而且排在写作站**之后**：
判定读的是模型写的标题与摘要（AIHOT 的 `reportText`）。骨架（`fact_json`）不是门槛，只是这条新事实的
名字 —— 观点、盘点类常常给不出骨架，拿它当门槛会让那些条目永远排在队里，把每一轮的预算占满。一条一次
判定，而且每定夺一条就把池子**重读一遍**：这一轮刚起的一件事，下一条报道就该能召回它，否则同一批里的
两条会各自起一件事。

11.4 **读取侧。** `views.collect` 还是先按规则分桶（`events.group`），再用 `stories.membership` 把已经
归好组的条目按库里那件事重新并桶；库里没有的条目**留在原来的桶里** —— 一个窗口里总会有几条还没轮到的
（预算截断、模型不可用），让它们掉出去等于页面忽然少几条，而它们并没有做错什么。没配模型时这一站不跑，
读取侧就是规则版：那是这套设计里唯一保留的「旧身份」，不是并行的第二套答案。

11.5 **模型不可用就收手。** 一条失败（没配 / 被限流 / 答案不合格式）就停这一轮，剩下的留在「未归组」
那一档，下一轮再来。半截地写下去会把这一批切成两半。

11.6 **提示词换版要重跑。** `prompt_version` 是内容哈希，排队判据是「还没写完 **或** 写完了但版本不是
现在这一版」（`db.feed_items_pending_llm`）。两档**各自**比自己的版本：只比 `llm_stage` 不够 —— 一条
已经写到 `full` 的旧行会每轮都被排进队列、每轮只写回一个空的 `full` 补丁，永远追不上版本，白花钱而且
静默。改了提示词是个大动作：库里几千行要一条条重问，预算 (`maxItems`) 就是它一轮能走多远的闸门。

11.7 **换一套分组规则怎么重来。** `db.feed_group_clear()` 清掉三张表（条目一条不动），下一轮按新提示词
从头分。这是 `regroup` 的最小可用形状；「重分组期间那一条不算证据」还没有（见 `ALIGN-AIHOT.md` 4.8）。

## 12 精选评分档：分数从哪来、门槛怎么算（2026-10-05 落）

12.1 **顺序：先评分，再决定写多好，最后才谈翻译。** 一条材料进写作站后依次走
`selection-score`（独立评两次）→ `understand`（均值 ≥ 50）**或** `summarize`（均值 < 50）→
`translate`（入选、原文不是中文、真有正文）。评分只看「谁、做了什么」的原文标题与正文，是这几档里
最便宜、也最该先问的一档；理解与翻译都要等分数说话，否则一批注定落选的稿子也在花最贵那档的钱。
这之前是「先理解、再看规则分决定要不要译」，顺序是反的。

12.2 **两次独立评分，存均值。** 每次调用只回 `{attentionScore}`（`prompts/selection-score.md`），
两次的分数记在 `feed_items.llm_scores_json`，均值（保留一位）记在 `feed_items.score_llm`。页面上
印的是均值；入选判据用的是两次之和 ≥ 两次门槛 —— 一次评分会把「这稿写得好不好」与「这件事值不值得
看」混在一起，而评两次的差本身就是这条判断稳不稳的信号。
输入里**故意没有来源名与分级**：评分只评事件，门槛那一层才按分级算。

12.3 **门槛按信源分级。** T1 60 / T1.5（库里写作 `T1_5`）65 / T2 76，与 AIHOT 的
`industry/selection.ts` 同数。表里没有的分级不参与精选评分，只进「全部动态」。
顺带修掉一处静默：`analysis.TIER_BONUS` 一直写的是 `T1.5`，而库里存的是 `T1_5` —— 官方账号那一档
的加分从来没生效过。

12.4 **分到地板（`UNDERSTAND_FLOOR` = 50）用理解档，没到只写标题与摘要。** 精选线附近的那一批
要写得好一点（它们会出现在全部动态里，也可能下一轮进了精选），再往下的只写两样，理由、骨架、实体
都不写 —— 那是 `prompts/summarize-*.md` 的活（按材料分派，见第 16 节），比理解档便宜，也比
「什么都不写、页面上留英文标题」好。
分界与命中都会写进 `llm_stage`（`summarize` / `understand` / `full`）。

12.5 **没配模型时的兜底。** 评分没拿到分（模型不可用、这一档不参与精选）时，入选与否退回规则分
（`analysis.CURATED_MIN_SCORE`）；不参与精选的分级则一律不进。这是这套设计里唯一保留的「旧身份」，
不是并行的第二套答案。

12.6 **按用途挑模型。** `feed/capability.py` + 系统设置的「按用途挑模型」六行：评分、理解、摘要、
结构、翻译、归组各可以指一个模型，留空就用 `llm.model`。读的时候现读并缓存一分钟，改完下一次调用生效。
以前只有一个模型，想给评分换便宜档就得给全站换。

12.7 **提示词换版要重跑。** `prompt_version` 是一串 token（逗号分开，一档一段），改哪一档就重跑
哪一档：写作档（理解/摘要）看有没有命中任一现行 token；评分与翻译是「写过才有 token」的档，token
不是现役的就重写。排队判据用的是**串里有没有**这一版，不是「开头是不是它」—— 开头那一段是评分档的
token，按前缀比会让每一行永远追不上版本，而且完全静默。两个写作档共用一份字，所以换档时
要顶掉另一档的 token：上次按理解档写、这次分掉到地板以下只写了便宜档的行，不能继续留着理解档的
token，否则下回分再涨上来它会拿便宜档的字冒充理解档的字，同样完全静默。

12.8 **落地位置**

| 东西 | 在哪 |
| --- | --- |
| 评分提示词 / 便宜档提示词 | `feed/prompts/selection-score.md`、`prompts/summarize-*.md`（六份） |
| 门槛、地板、评分次数 | `feed/writing.py` 的 `SELECTION_THRESHOLDS` / `UNDERSTAND_FLOOR` / `SCORE_CALLS` |
| 能力 → 模型 | `feed/capability.py` + `config.SYSTEM_KEYS` 的 `llm.models.*` |
| 两列新数据 | `feed_items.score_llm` / `llm_scores_json`（schema v19） |
| 页面「AI 评分」与精选筛选 | `writing.apply_item` 盖分 → `views.items_view` 按 `item.selected` |

## 13 结构档与标签三分：类别、标签、主体、骨架（2026-10-05 落）

13.1 **结构另起一档，不写读者看的字。** `prompts/structure.md` 抽四样：类别（`category`）、标签
（`tags`）、主体（`subjects`）、事实骨架（`fact`）。它不写标题、摘要、理由，也不打分，所以与理解档
分开 —— 改一次标签词表不必把最贵的理解档整库重跑。它与评分并列：对每一条材料都跑，不看分级。

13.2 **骨架与 subjects 从理解档搬进结构档。** 以前理解档一次写五样（标题 / 摘要 / 理由 ＋ 骨架 ＋
subjects），结果「改标签词表」和「改写作口径」绑成一件事。现在理解档只写三样（`title_zh` /
`summary` / `reason`），骨架与 subjects 只由结构档写；两档都写同一格会让「这一格按哪一档写的」没有
答案。搬家的代价是一次性的：两份提示词的版本都变了，库里每一行按新口径各重跑一遍。

13.3 **标签过白名单，第一格必须是分类标签。** `taxonomy.normalize_tags` 照 AIHOT 的
`vocabulary.normalizeTags` 逐条对齐：只认词表里的写法、同义词先归一、去重、上限 6 个（分类标签算
第一个）；分类标签排第一，一个都没有就用 `fallback`（规则版 `taxonomy.classify` 读出来的类别，
确定性兜底，不为这一格再问一次模型）。白名单外的一律丢掉 —— 漏进角标的词，筛选栏筛不到它，那是
一个静默的洞。

13.4 **实体角标只看白名单里的那几家。** 结构档给的 `subjects` 过实体词典（`entities.yaml`）那一道
筛，然后**只有落在 `taxonomy.ENTITY_TAGS` 里的实体才印角标**（AIHOT 的 `displayTag` 那道闸）；词典
里其余的实体仍然进 `subjects`，用于分组与更深的筛选，只是不上卡片 —— 否则筛选栏会长出六十多个
没有内容的 chip。

13.5 **词表也进版本。** 结构档的 `prompt_version` ＝ 提示词文件 ＋ 渲染进去的那几张词表
（`writing.structure_version()`）。只哈希文件的话，改了 `taxonomy.py` 里的词表而提示词一个字没动，
库里那些按旧词表抽过的行不会重跑，旧标签会一直冒充新词表。

13.6 **回退。** 结构档失败（模型没配、超时、答案不合格式）时这一条停在上一档，`llm_at` 把它推到
`retryHours` 之后；页面上照着规则版 `taxonomy.classify` 印 —— 没配模型时页面不空、不报错，是这套
设计唯一的底线。

13.7 **落地位置**

| 东西 | 在哪 |
| --- | --- |
| 结构提示词（词表用 `{{...}}` 替身，`read_prompt` 渲染） | `feed/prompts/structure.md` |
| 词表、同义词、归一 | `feed/taxonomy.py` 的 `CATEGORY_TAGS` / `TAG_SYNONYMS` / `normalize_tags` |
| 档位与补丁 | `feed/writing.py` 的 `STRUCTURE_CALLS` / `structure_version()` / `write_one`；这一轮放行哪几档由档位定（`pipeline.PRESETS`，3.6） |
| 两列新数据 | `feed_items.category_llm` / `tags_json`（schema v20） |
| 能力 → 模型 | `capability.py` 的 `structure` ＋ 设置页「结构抽取」 |
| 页面类别 / 标签 / 实体 | `writing.apply_item` 盖 → `views.item_payload` |

## 14 向量召回、热度口径、时间线判定（2026-10-05 落，三期收尾）

14.1 **召回两条线，永不混。** 配了 `/embeddings` 端点就整批走向量余弦（召回线 0.6，AIHOT 的
`RECALL_MIN_COSINE`）；没配、或者这一批里有一条没拿到向量，就整批退回字符二元组（线 0.25）。**两条
线不能混**：尺度不同，混出来的结果既不是向量召回也不是字面召回，而且完全静默 —— 所以
`embeddings.warm` 是整批语义，一条缺失就整批回 `None`。端点返回 404（网关没有 `/embeddings`）不是
异常，是"退回字面"，它不该让分组整轮停摆。落地位置：`feed/embeddings.py`、`stories._group`。

14.2 **热度看的是窗口，不是编号。** 过去 48 小时里，每家独立来源取它**最新**的那一次发言（问的是
"这家现在还在说吗"），按 24 小时半衰期折算成热度。旧口径是 12 小时半衰期、没有窗口、每家取最早那
一条 —— 一件旧事会一直累加热度，最后挤掉今天真在发生的事，页面上就是"热点榜混进了别的事"。入榜还
要一条：至少两家在说（`heat.eligible`），一家之言是通稿。

14.3 **badges 是同一批数字的三种读法。** `surge`（这 6 小时加入的来源过半且 ≥ 3 家）/ `new`（第一
次出现不到 6 小时）/ `rising`（比 6 小时前涨 15% 以上），三条互斥、只印最先成立的那一枚。它们由
`heat.badges` 判、`views.story_payload` 给 `hot_badges`、`bits.tsx` 的 `HotBadge` 翻成词 —— 页面
不重新判断任何一条规则。

14.4 **时间线一条规则，两个入口共用。** `materials.decide_timeline`：源说的时间比我们读到它还晚超
过 1 小时就当没说（`FUTURE_TOLERANCE_HOURS`），用发现时刻代替；比我们读到它早超过 48 小时就标成
**历史**（`STALE_ON_DISCOVERY_HOURS`）。前者救窗口（一条时标跑到三天后的记录会在窗口判定里挤掉今
天的事），后者救事件图。落地位置：`collect._stamped`（唯一盖时间戳的入口）＋ `materials.is_historical`
＋ `views.collect` 把历史条目单独成组。

14.5 **历史不立事件、不加热度。** 一条被翻出来的旧闻照常列出来、照常点得开，但不进今天的事件图 ——
进去了它就会以"今天第一次出现"的身份和今天的新闻抢位置，一家旧报道就能把一件事顶成"两家在说"。
`is_historical` 靠 `seen_at`，而 `seen_at` 是**第一次**读到它的时刻（`feed_items_put` 的 upsert 不再
刷新它）：每次重读都刷新的话，一条老记录会越读越"新"，永远判不成历史。

14.6 **落地位置**

| 东西 | 在哪 |
| --- | --- |
| 向量端点与整批语义 | `feed/embeddings.py`（`CH_EMBEDDING_*`，内存 TTL 1800s） |
| 召回走哪条线 | `stories._group` |
| 热度口径与 badges | `feed/heat.py`（`WINDOW_HOURS` / `HALF_LIFE_HOURS` / `MIN_PARTICIPANTS` / `badges`） |
| 入榜门槛 | `views.ranked_stories` 的 `heat.eligible` |
| `hot_badges` 出参 | `views.story_payload` + `api/v1/schemas.py` 的 `FeedStoryOut` |
| 时间线规则 | `materials.decide_timeline` / `materials.is_historical` |
| 时间戳入口 | `sources/collect.py` 的 `_stamped` |
| 历史单独成组 | `views.collect` |
| 第一次读到的时刻 | `feed_items.seen_at`（upsert 不刷新） |

14.7 **还欠着的一件。** AIHOT 的每小时快照（`story_heat_hourly`）与排行榜落库（`hot_rankings`）没有
做 —— 我们的走势线仍由当前证据现算。差别只在这条线会不会随新条目回溯改写，不影响排序与入榜；等
源体检（1.9）有 `last_ok_at` 之后一起做，"某个小时是不完整的"那个判断才有依据。

## 15 讨论帖与提示词片段（2026-10-05 落，四期）

15.1 **讨论帖是证据，不是报道。** X 上的监测账号（`config/feed/sources.yaml` 里
`participation_mode: hot_signal` 的那五个）不立事件。它们要么挂到别人已经立好的那件事上投一票热度，
要么"问过了、没挂上"记一笔。理由与 AIHOT 的 `groupSignal` 同一条：热点榜数的是"几家在说**这一次
发生**"，一条推文转发一句也算一家在说；但把它当报道印出来，读者看到的就是一条没有内容的新闻。

| 位置 | 做什么 |
| --- | --- |
| 源画像 | `feed_sources.participation_mode`（editorial \| hot_signal \| isolated） |
| 读它 | `sources/registry.py` 的 `Source.participation` |
| 排队 | `db.feed_items_for_grouping`（挂过的 / 问过的不再排第二遍） |
| 编排 | `stories._signal` |
| 落库 | `feed_story_signals`（`story_id` 为空 = 没挂上） |
| 读取侧 | `stories.membership`（与报道一起重新分桶）+ `views.evidence`（不印） |
| 判定 | `grouping.judge_signal` / `grouping.signal_target`，提示词 `prompts/group-signal.md` |

15.2 **挂靠的三条路，由便宜到贵。** 一条帖子要挂到哪件事上，先后是固定的：

| 路 | 判据 | 花一次调用吗 |
| --- | --- | --- |
| 指向 | 它转发/回复了库里那一条（网址对上） | 不花（`signal-native`） |
| 直挂 | 召回余弦 ≥ `grouping.SIGNAL_AUTO_COSINE`（0.92） | 不花 |
| 问一次 | 召回余弦 ≥ `grouping.SIGNAL_MIN_COSINE`（0.72），取 `SIGNAL_TOP`（4）条交给模型 | 花 |
| 没挂上 | 没候选、没配向量端点、或模型给的都不够格 | 记一笔 `signal-unmatched` |

反应线 `SIGNAL_REACTION_MIN`（0.8）：帖子被判成"对这件事的直接反应"才收。顺手评论一句不算 ——
收了它就会把两件事连成一件。**没配向量端点时整档退化成"只记一笔"**（AIHOT 同一条）：这一档的判据
就是召回分，而字面相似度在几十字的推文上量不出可信的值。

15.3 **读取侧：数它一家，但不印它。** `heat.observations` 读 `event.items`，所以一条挂上的帖子照样
算一个独立参与方；印出来的那几个列表（`views.collect` 的 `items`、`story_payload` 的 `items`、
`other_reports`、`story_days`）先过 `views.evidence` 那一关。只剩证据、没有报道的事不成事件 ——
它会是一张没有正文的空卡。

15.4 **提示词片段：共用规则只写一份。** `prompts/rules-*.md` 与 `safety.md` 是片段，靠
`{{> name}}`（AIHOT 的 `{{> file}}`）插进各档。约定两条：

1. **片段进版本。** `writing.version()` 哈希的是"这份提示词读到的每一个文件"，所以改共用规则一个字，
   用到它的每一档都重跑。只哈希主文件的话，那些按旧规则写过的行不会重跑而规则已经换了，完全静默。
2. **没有片段的提示词，版本与从前逐字相同** —— 不为一次换写法白花一轮模型钱。
   环与缺文件都直接报错（`ValueError` / `FileNotFoundError`），不留白。

| 片段 | 用在哪几档 |
| --- | --- |
| `safety.md` | 全部（10 档） |
| `rules-anti-hallucination.md` | 除 `group-*` 之外的写作档 + `group-*` 也带（安全） |
| `rules-self-contained-title.md` | `understand.md`、`summarize-article/long-post/short-post.md` |
| `rules-answer-first-summary.md` | `understand.md`、`summarize-article/long-post.md`（短帖是译，不套） |
| `rules-domain.md` | `understand.md`、`summarize-*.md`、`structure.md`、`translate-*.md` |

15.5 **一次重跑是预期的。** 加入片段会改变这些提示词的版本，所以下一轮写作站会把窗口里的条目重新
问一遍。这是"改一个字就是一个新版本"的直接后果，不是 bug。

15.6 **分档摘要已落（见第 16 节）。** 4.7 输入哈希、4.8 合并纠错、4.10 后续与相关 —— 还在清单里
排着。

## 16 便宜档分档：文章写摘要、短帖直接译（2026-10-05 落）

16.1 **一份提示词管不了三种材料。** 文章要 80-160 字的摘要；短推文要的是**译文**；长推文要摘要，
但推文里的数字不能当细节删。以前三合一（`summarize.md`），于是一条三十字的推文也被要求凑八十个字，
模型只能把原文没有的意思补出来。现在按 AIHOT 的六份分派：

| 材料 | 提示词 | 写什么 |
| --- | --- | --- |
| 文章 / 公告 / 博客 | `summarize-article.md` | `title_zh` + `summary`（80-160 字） |
| 同上、正文为空 | 再附 `summarize-article-empty.md` | `summary` 写空串，不拿标题脑补 |
| X 短帖 | `summarize-short-post.md` | `title_zh`（10-15 字）+ `summary`（**译文**，不是摘要） |
| 短帖带引用 | 再附 `summarize-short-post-quoted.md` | 主推文没信息量时改概括引用推文 |
| X 长帖 | `summarize-long-post.md` | `title_zh` + `summary`（具体数字优先保留） |
| 长帖带引用 | 再附 `summarize-long-post-quoted.md` | 把引用的关键上下文整合进摘要 |

引用推文与空正文这两段是"这一种情况该怎么写"的**附则**，接在系统提示词后面；材料本身（含引用
正文）照旧走用户消息里的材料块。挑哪一份提示词由材料说了算（`summarize_system`）。

16.2 **两把尺，各管各的事。** `is_short_tweet`（汉字占三成按 100 字算，其余按 500，AIHOT 的
`isShortTweet`）决定走短帖档还是长帖档；`short_post`（挖掉网址后 < 60，AIHOT 的 `X_MIN_CHARS`）
决定翻译档要不要再译一遍正文。一条 80 字的英文推文是短帖，但正文仍然要译 —— 用一个数会把这两件事
搅在一起。

16.3 **不问模型的两种情形也记版本。**
1. 短帖本来就是中文（`needs_short_translation` 为假，AIHOT 的 `verbatim`）：它自己就是稿子，
   `title_zh` 与 `summary` 都抄原文；
2. 文章正文短于 20 字（AIHOT 的 `none`）：中文原标题照留，`summary` 空串。

两种情形都写 `llm_stage = summarize` 与现行 token —— 否则每一轮都会再把它们排进预算（不花钱，
但永远"欠一遍"，页面也就永远显示"还没写完"）。

16.4 **太长的摘要就地压短。** `answer_first_ok` + `compact_answer_first`（AIHOT 的 `finalizeCopy` /
`compactAnswerFirstSummary`）：超过 200 字、或句数不对，先在本地按句号、再按逗号截到 190 字以内，
不为那几个字再问一次模型（那一次要钱、要等，而且未必更准）。截的时候只落标点处，绝不切在名字或数字
中间。短帖不走这条路 —— 它的 `summary` 是译文，不是"答案前置"。

16.5 **六份共用一个版本。** `summarize_version()` 把六份的哈希拼成 `summarize@<hash>`（AIHOT 的
`PROMPT_VERSIONS.summarize`）："这条是按哪一版写的"要能用**一个** token 回答。`drop` 按 token 的
**名字段**（`@` 之前）整段比，不是前缀比 —— 所以旧的 `summarize.md@...` 会被一起清掉。

## 17 综述的输入指纹：判「要不要重写」看哈希，不看条数（2026-10-05 落）

17.1 **条数不是输入。** 以前 `digest_version` 存的是上次写综述时的**报道条数**，条数没变就不重写。
它挡不住两件真会发生的事：同一条报道换了标题或摘要、拿掉一条又添一条 —— 条数一样，而旧综述说的已经
不是这件事现在的样子。现在存的是**输入指纹**：全部可用报道按 `源|外号` 排序后，把进得了综述的那几个
字段（中文标题、摘要、来源、时间）拼起来哈希（AIHOT 的 `digestInputsHash`）。

17.2 **只哈希进得了综述的字段。** 正文译文换一块不算输入变 —— 否则一条报道重译就会白花一次模型钱，
而综述里根本引用不到那段。

17.3 **指纹要按当前报道现算，所以判据搬到 Python。** SQL 算不出哈希，`feed_stories_for_digest` 只筛
「窗口内 + 有报道」（顺带把上次的指纹与 id 集合带出来），比较在 `feed/digest.py` 里做。`limit` 回到它
本来的意思：调用方按预算数**模型调用**次数，不再按候选行数截断。

17.4 **能增量就增量。** 上一版覆盖的报道一条都还在、内容一个字没变时（AIHOT 的 `proven`），把上一版
综述一起递给模型，并把新增的报道标【新】—— 这一趟是接着写，不是从头猜。少了任何一条就不冒这个险：
按「从头重写」走，并明确要求不要沿用旧版说法。沿用一段已经对不上的话，比多花一次钱坏得多。

17.5 **落笔是原子的。** 文字、指纹、id 集合（`digest_inputs` / `digest_ids`）一次写完 —— 只有它们和
这段文字出自同一批输入时，下一次才敢说「输入没变」。id 用 `源|外号`（表的主键），不用行号：行号会随
重抓变，拿它当身份，指纹会假变。

17.6 **还欠着的一半。** `derived-content.ts` 的另一件事是**输入失效**：成员被移走、报道权限变了，要
当场清掉事件与事实的派生文字并把版本 +1。那件事跟「改错与合并」（4.8）是同一处，在那一期做。


## 18 合并与相关：两个根、两次判定、旧 id 跟到存活那头（2026-10-05 落，四期 4.8）

判定站一次只回答"这条报道和每个候选是什么关系"。一条报道同时**牢牢绑住**两件事（同一次发生 / 直接
后续，置信 ≥ 0.8）时，那两件事可能本来就是一件 —— 这批边落 `feed_story_ties`，`feed/consolidate.py`
读它，在分组站之后、综述站之前跑。

### 18.1 比什么

| 项 | 口径 |
| --- | --- |
| 触发 | 一条报道绑住 ≥ 2 件（`feed_story_tie_pairs`，按报道分组） |
| 比的 | 两件的**根**（`feed_story_root_report`：根事实 + 代表报道），不是最新那条 |
| 锚点 | 早的当锚点（代表报道 `published_at` 早的在前），晚的并进去 |
| 第一次 | `grouping.review`（`group` 档），`firmly_tied` 线 0.8 |
| 第二次 | 反着再读一遍（`group_review` 档），线 0.75（`STORY_REVIEW_MIN_CONFIDENCE`） |
| 结论 | 两次都过才合；一次不过只记账（`kept`） |
| 盘点 | 根事实里有 `roundup` 关系的事**永不合并**，也不互为相关 |
| 预算 | `maxItems` 数"比几对"：一对 1 次调用，过线再 +1 次 |

### 18.2 合并搬什么

| 搬 | 不搬 |
| --- | --- |
| `feed_facts.story_id` → 保留那件 | 报道本身（它属于哪个事实不变） |
| `feed_story_signals`（讨论证据） | `feed_items` 的任何字段 |
| `feed_story_ties` 的边 | |
| `first_at` / `last_at` 取极值 | |

被并的那件留一行 `merged_into = 保留那件`：`s:<id>` 是会被贴出去的键，删掉它页面就 404，而它只是换了
名字。读取侧 `views._live_story` 经 `db.feed_story_leader` 一路跟到存活那头（AIHOT 的 `liveStory`）。

### 18.3 成员变了，结论就作废

合并之后对**保留那件**调 `feed_story_invalidate`：清标题、综述、最新进展、输入指纹，标题退回代表报道
的。下一轮综述站按新的成员重写。**留着上一版综述配新的成员，是页面上说了一件没有人再算过的事。**

### 18.4 相关（合不了的那些）

至少**两条**报道把两件事绑在一起（关系都是 same_occurrence / same_story，置信 ≥ 0.8）、两头都没被合并、
都不是盘点起头 → 互相记一行 `feed_story_links`。只加不减：合并掉的那一头在读取时自然落下去。一条边太
容易是"模型在一串候选里顺口说了一句"，而挂错的代价是读者以为它们是一件。数据源已就绪，页面还没读
（4.10）。

### 18.5 人工决定

| 事 | 在哪 |
| --- | --- |
| 记一条人工决定 | `db.feed_override_set` → `feed_grouping_overrides` |
| 自动分组 | `feed_items_for_grouping` 排除有决定的行；`stories.run` 写之前**再读一次**（判定要几十秒，人可能就在这中间点了「放在这里」） |
| 显式「重新分组」 | `db.feed_override_clear`，下一次自动分组再判一遍 |
| 清空分组结果 | `feed_group_clear` 连 `ties` / `links` / `overrides` 一起清 |

### 18.6 还没做

- 管理台按钮：目前只有 db 层的入口，人还没有地方点（AIHOT 在 admin 上）。
- 审计：合并 / 纠错没有记 actor 与理由（AIHOT 落 `audit`）。
- AIHOT 写入事务里还锁成员（`lockStoryMembership`）：我们 SQLite 单写者，先不做，等并发真成问题再补。

## 19 热度口径对齐 AIHOT：量纲、五态、标签、入榜门槛、落后源（2026-10-05 落，四期 4.9 前半）

这一节改的都是**口径**，不是新功能：页面上那几个数以前和 AIHOT 差一点，现在同源同判。热点榜的
序列仍然按需现算（不落库），下一节把每小时快照与 7 天曲线补上。

### 19.1 一个数、两个单位

| 事 | AIHOT | 我们（改后） |
| --- | --- | --- |
| 排序用的热度 | `heat`（折合几个满血来源） | 同 |
| 页面印的指数 | `heatIndex = round(heat*100)/10`：10 倍、**一位小数** | `heat.index()` 同式（原为 20 倍取整） |
| 卡片上那个数 | 渲染时 `Math.round(heat)` | `Math.round(heat_index)` |
| 走势线 | `SPARK_HOURS = 24`，**每小时一个点** | `heat.SPARK_HOURS = 24`（原 12 点 × 2 小时） |

排序始终用原值，量纲只影响印出来的样子 —— 两处不一致的图比没有图更糟，所以走势线最后一个点必定
等于卡片上那个数（`test_the_line_is_one_point_per_hour` 钉住）。

### 19.2 五态走势，不是一个百分数

| 态 | 判据 | 页面写 |
| --- | --- | --- |
| `new` | 6 小时前这件事还不存在（`heat_prev <= 0`） | 新上榜 |
| `unknown` | 有旧的，但**可比**那组是空的 | 暂不比较 |
| `up` / `down` | 涨跌超过 ±10%（`trend_pct`） | ↑/↓ N% |
| `flat` | 其余 | 持平 |

涨跌比的是**可比**那一组（AIHOT 的 `heat_obs` / `heat_prev_obs`）：一家源正在落后（`behind`），或
这家是 54 小时内才接入的（`source_since > 上一窗口起点`），都不进这一比 —— 一个刚接入的来源会把涨幅
算成几百个点，一个还没抓完的来源会让"今天比昨天冷"变成它自己造成的。**副作用要记住：数据库是新的
时候，名录里每一个源都是"刚接入"，于是趋势会连着两天写「暂不比较」。** 这是 AIHOT 的判据本身，不是 bug。

### 19.3 标签各自成立，不是三选一

`surge`（这 6 小时新加入的来源 ≥3 家且占一半以上）、`new`（首次出现不到 6 小时）、`rising`
（不是 surge 且涨过 15%）三条**各自判各自印**：刚发生又被三家同时跟进的事同时带 `surge` 和 `new`。
页面从"取第一枚"改成**全画**（`HotBadge`）。

### 19.4 入榜要有发布源，来源数只数发布源

| 事 | AIHOT | 我们（改后） |
| --- | --- | --- |
| 入榜 | `participants >= 2` **且** `editorial_participants >= 1` | `heat.eligible` 同两条（原为"或够精选就放行"，后门已去掉） |
| 卡片上的"发布来源" | `sourceCount = editorial_participants` | `source_count`（原为全部 `source_id` 去重） |
| 另外两个数 | `participantCount` / `signalCount` | `participants` / `signal_count` |

全是讨论帖凑出来的"两家"，是有人在聊，不是在报 —— 它进不了热点榜，也不再用讨论帖的数量冒充来源数。

### 19.5 落后源与接入时间从哪来

`db.feed_source_clocks()` 取 `feed_sources` 的 `last_ok_at`（最后的**成功**，不是最后一次尝试）、
`interval_minutes`、`created_at`；`heat.source_clocks()` 把它翻成时钟，`heat.clocks_behind(clocks, at, grace)`
判落后：看现在（`grace=True`）三个间隔（至少 90 分钟）没有成功就是落后。读取侧每趟都带上它。

### 19.6 顺带对齐的写作档三处

| 事 | AIHOT | 我们（改后） |
| --- | --- | --- |
| 结构档温度 | 0.2 | 0.2（原 0） |
| 精选分印哪个数 | `Math.floor(sum/2)` 两次均值的**下取整** | `math.floor`（原四舍五入到一位小数） |
| 理解档地板边界 | `sum > UNDERSTAND_FLOOR*2`：**高过** 50 才算到 | `mean <= UNDERSTAND_FLOOR` 才算便宜档 |


## 20 热度快照与榜单快照：页面读的是写下来的那一份（2026-10-05 落，四期 4.9a-e）

### 20.1 两张表

| 表 | 键 | 一行是什么 | 谁写 | 谁读 |
| --- | --- | --- | --- | --- |
| `feed_story_heat_hourly` | `(story_id, hour)` | 一件事在一个小时的热度：`heat`（页面那个单位）、`participants`、`cohort`（发布源家数）、`complete` | `snapshot_heat.snapshot` / `backfill` | 卡片上的线、详情页那条曲线 |
| `feed_hot_rankings` | `id` | 一份榜：`computed_at`、`rule_version`、整张榜的 `entries_json`、`evidence_json` | `snapshot_heat.rank` | `GET /feed/hot`、详情页的名次 |

`story_id` 存事件的键（`s:<id>` 或规则桶的哈希键），不是外键：规则桶还没落进 `feed_stories`。
两张表都是派生物，空表只说明"还没落过快照"。

### 20.2 一小时怎么落（`snapshot`）

1. `hour` 取整到小时，`behind = clocks_behind(clocks, hour, grace=True)`。
2. 每一件事一行：`heat = index(row.heat)`（**页面单位**，与卡片上那颗数同源）、`complete = (row.behind == 0)`。
3. 再修旧的：`[hour-48h, hour)` 里 `complete = 0` 的小时用 `grace=false` 重算，只留 `behind = 0` 的行。
4. 剪掉 7 天以前的格子（曲线只画 7 天；这一条 AIHOT 没有，是我们为 SQLite 加的上限）。

`complete = 0` 的意思是"那一刻有源没把该说的说完"，不是"那一刻很冷"。

### 20.3 落后源的两副面孔（`grace`）

| 看哪一刻 | `grace` | 判据 | 为什么 |
| --- | --- | --- | --- |
| 现在 | `true` | 三个间隔（至少 90 分钟）没成功就是落后 | 它可能正要说话，现在下结论算早了 |
| 过去某一小时 | `false` | 那之后成功过一次就不算落后 | 证据带着源自己的时间，它该说的都说了，那一格定了 |

### 20.4 榜单怎么读

- `rank(at)`：算一遍并落一行（`rule_version = heat.RULE_VERSION`）。
- `latest(at)`：读最新一份已发布的榜；`rule_version` 对不上、或超过 `RANK_TTL_MINUTES = 5` 分钟，答 `None`。
- `hot_payload(at)`：先 `latest`，没有就 `rank` 一次再读；还不行退回现算（`views.hot_view`）。
- 榜单留 30 天，小时格留 7 天。

于是"卡片上的名次"和"详情页说的榜内第 N 名"读的是同一份写下来的结果，不是各算一次。

### 20.5 线怎么画

| 线 | 来源 | 形状 |
| --- | --- | --- |
| 卡片上的迷你线 | `sparkline(ids, 榜单的 computed_at)` 读小时表 | 25 个**小时**格子（24 小时 + 当前），缺的补 `null`，线在那里断开 |
| 详情页的曲线 | `series(story_id, now, days=7)` | 逐小时 `{hour, heat, participants}`，只含 `complete = 1` |

`series` 只数**从头看到尾**的参与者（源接入时间晚于第一个格子的窗口起点就排除）：一个源是后来才
接入的，把它算进更早的小时，等于把一条平线画成一条上升的线。

### 20.6 两条已知副作用（新库上会看到）

- **迷你线先退回现算。** 刚上线的库里每个故事只有当前那一格，`sparkline` 只有一个真实点，画不出线。
  读取侧在"真实点 < 2"时不换，退回 `story_payload` 里现算的那条 24 小时线（`snapshot_heat._drawable`）；
  快照攒够两格后自动读库。
- **7 天曲线先是空的。** `series` 要求参与者从头到尾都在，而新库里所有源都是刚接入的，
  `source_since > 窗口起点` 对每一家都成立 → 没有参与者 → 空。成因与 §19.2 的"趋势连日 unknown"相同。

## 21 写作档四处对齐 AIHOT：标签、退档、容错、调用参数（2026-10-05 落，五期 3.17/3.18/2.4a/2.4b）

### 21.1 标签两档都写，理解档说了算（3.18）

| 情况 | 最终 `tags_json` |
| --- | --- |
| 理解档给了标签 | 理解档那一组（类别归 `category_llm`，主题进 `tags`，实体进 `entities`） |
| 理解档一个都没写 | 结构档那一组原样保留 |
| 没到理解档（均分 50 及以下） | 结构档那一组 |

`subjects` 推出来的实体标签照旧补在 `entities` 后面 —— 那是另一条来源，不是标签档的判断。
理解档的版本因此也把**词表**算进去（`understand_version()` = 提示词 + 词表）：改一次词表，按旧
词表抽过的条目会重跑理解档，与结构档同一把尺。

**代价（一次性）**：`understand.md` 的内容与版本都变了，库里已写过理解档的条目会在下一轮重跑
一遍理解档。这是对齐的必然结果，不是回归。

### 21.2 只有「内容审核拒绝」才退档（3.17）

| 失败 | 行为 |
| --- | --- |
| 上游内容审核拒绝（`llm.ContentRefused`） | 改走便宜档写标题与摘要（AIHOT 的 `?? await runSummarize()`） |
| 限流 / 超时 / 答案不合格式 / 没配模型 | 照旧整条失败，`llm_at` 推到 `retryHours` 之后 |

判据两处：400 的响应体里出现 `contentFilter` / `"1301"` / `content_filter`，或 200 但
`finish_reason` 是内容过滤而正文为空。两条都收进 `ContentRefused`（`LLMUnavailable` 的子类），
写作站 `except ContentRefused` 先接住它。**其余错误不许退**：把限流当成"写不了"，会让一整轮
静默地全降成便宜档。

### 21.3 JSON 容错按 AIHOT 的三步（2.4a）

`llm.complete_json` 依次容忍：整段围栏 → 首个 `{` 到末个 `}` 之间的对象 → 字符串里的裸控制字符
（换行 / 制表符 / 其它 `\uXXXX`）。三步都过不去的仍然失败 —— 猜一个坏草稿，等于让页面说出一件
没有人决定过的事。多行推文正是这材料的常态，不是边角。

### 21.4 调用参数按档给（2.4b）

| 档 | temperature | maxTokens | 超时 |
| --- | --- | --- | --- |
| structure | 0.2 | 800 | 旋钮 |
| understand | 0.2 | 16384 | `max(旋钮, 180s)` |
| summarize | 0.2 | 2048 | 旋钮 |
| score | 0.2；`glm-5.3-flash-selection` 用 1 | 1024；同上用 65536 | `max(旋钮, 120s)`；同上 180s |
| translate | 0.2 | 全局 `CH_LLM_MAX_TOKENS` | 旋钮 |

分档超时是**地板**不是盖子：旋钮调得更长时听旋钮的，免得一次慢回答被当成失败，下一轮再来一遍。
全局 `CH_LLM_MAX_TOKENS` 是表外那一档的兜底（写 `0` = 不设上限，交给网关）。

## 22 采集的两处口径：诚实 UA 与「这算不算正文」（2026-10-05 落，五期 1.13/1.4b）

### 22.1 信息流车道报自己的名字（1.13）

| 车道 | UA | 为什么 |
| --- | --- | --- |
| 信息流（RSS 订阅端点、列表页、正文页） | `Mozilla/5.0 (compatible; CryptoHunterBot/1.0)` | 那些站点的 robots 与封禁规则按 UA 放行或封禁；装成 Chrome 是我们替读者做的决定 |
| 雷达（DexScreener / GMGN / GeckoTerminal 等 JSON API） | 原样不动（Chrome UA + curl_cffi） | 那些站点把 TLS 指纹与 UA 一起判，换掉只会静默地少拿到数据 |

某一个源确实要别的 UA，在 `config/feed/sources.yaml` 那一行的 `headers` 里写它 ——
`http.crawler_headers()` 认源自己给的头；UA 里**不带**联系网址，等有了公开站点再加 `+<site>/about`
(AIHOT 的 `DEFAULT_UA` 是那个形状)。

### 22.2 抽出来的正文短于 200 字就认输（1.4b）

`detail._MIN_BODY` 从 120 抬到 200，与 AIHOT 的 `MIN_BODY_CHARS` 同数。判的是**抽出正文后的
文字数**（`htmlbody.to_text`），不是页面的字数；不够就退回 og:description，再不够就交空串，让这条
留在 RSS 给的那句摘要上。**顺序**上补正文仍排在写作站之前（DESIGN §8.5），所以「材料只有标题与
摘要时先抓原文页再判」这一条早已成立；没对齐的是 AIHOT 的 `needsBody` 推迟（抓不到就干脆不评分）
与 teaser 判定（RSS 正文不足 1200 字且带 `read more` 只当摘要），那是 1.4d。
## 23 分析输入层与正文上限：存储一份、喂模型按档各一份（2026-10-05 落，五期 3.11/1.4a）

### 23.1 为什么非要把这件事独立成一层（3.11）

在此之前，「正文上限」只有一个数（`htmlbody.MAX_CHARS = 20_000`），它同时干两件事：**库里存多少**
和**喂给模型多少**。于是想按 AIHOT 把正文存到 60k，就等于把长文的模型输入一起抬三倍 —— 花的是三倍
的钱，而多出来的那一截对判定没有用。`api/app/feed/input.py`（AIHOT 的 `editorial/input.ts`）把这两件
事分开：库照 60k 存，每个判定档自己截自己的那份。

| 渲染器 | 谁读 | 正文上限 | AIHOT 对应 |
| --- | --- | --- | --- |
| `structure_material` | 结构档 | 7 000 | `buildMaterial` 的 `truncate(body, 7000)` |
| `context_material` | 预筛、理解档 | 60 000 | `renderContext` 的 `capBody` |
| `score_input` | 评分档 | 60 000 | `buildScoreInput` 的 `MAX_BODY_CHARS` |
| `summary_material` | 便宜档（摘要/短帖） | 文章 6 000 / 帖子 4 000 / 引用 1 500 | 三个 `build*Prompt` |

一次 `load`（`AnalyzeInput`）读完这一行，之后只渲染，不再回读库 —— 一条材料在一站里读几次库，就没
有人能回答「模型看到的是哪一版」。

### 23.2 上限变了，格式也补齐了三样（3.11）

材料里原本只有「来源 / 发布时间 / 原文标题 / 原文正文 / 候选实体」。现在补上 AIHOT 已有的三样，它们
各自有实际用处：

| 新字段 | 谁需要它 | 为什么 |
| --- | --- | --- |
| **作者** | 理解档、摘要档 | 判断「这是当事方在说话还是转述」是 `authorRole` 的依据 |
| **原文链接** | 判定站全部 | 身份守卫要按发布域认出主体（3.12）；没有 url 就只能靠名字猜 |
| **材料质量** | 预筛、理解档 | 「完整正文 / 仅摘要 / 抓取失败只剩标题」决定这条能说多满 |
| **媒体** | 预筛、理解档 | 只说「N 张图」：模型看不到图，但要知道有个设备/截图是本体的一部分 |

评分档**没有**来源名与分级，这一条与 AIHOT 的 `buildScoreInput` 一致：输入里没有名气，模型就没法拿
名气加分。它同时补上了引用推文（引用是材料而不是噪音）与「正文为空就退回标题」。

### 23.3 与 AIHOT 仍有意的出入（记在这里，不许再当新差异报一遍）

- **时间写 ISO 8601（带偏移量）**，不换成「北京时间」字符串：ISO 没有歧义，AIHOT 自己在
  `buildMaterial`（北京时间）与 `renderContext`（ISO）两处就不一致。
- **材料字段用中文标签，不用 `【标题】`**：字数与语义一一对应，换标签是纯格式。
- **只有一处源头**：`quoted_parts` / `quoted_block` 的解析与格式都在 `input.py`，写作站调它，不再各写一份。
## 24 预筛档：先问「这条材料是不是本行业的」（2026-10-05 落，五期 2.1）

### 24.1 它省的是整条预算，不是一次调用

预筛排在**所有花钱的档之前**（结构、评分、摘要/理解、翻译）。判为 `BLOCK` 的那一条，后面几档
一次都不打 —— 省下的是整条的分析预算，而不是这一档自己的钱。代价是每条材料多一次调用（AIHOT
也是这么付的），所以它必须便宜：`temperature = 0`、`max_tokens = 512`（AIHOT 的
`PrefilterSchema` 那两个数），回答只有一个标签加一句依据。

| 标签 | 含义 | 之后 |
| --- | --- | --- |
| `PASS` | 有实质的行业事实或观点 | 照旧走评分与写作 |
| `BLOCK` | 材料足以确认只有普通互联网 / 传统金融 / 个人日常 | 短路；`llm_stage = blocked`，一个字不写 |
| `UNKNOWN` | 只有代词、表情、看图/看视频 | 放行 —— 它的材料已经到头了 |

### 24.2 三条不许省掉的纪律

- **BLOCK 要有正面依据**：不能拿「未提及」当理由。判不出来是 `UNKNOWN`，不是 `BLOCK`。
- **材料只有标题时 BLOCK 降级 UNKNOWN**（AIHOT 的 `missingEvidence`）：那是「等材料」，不是
  「无关」。这一条防止正文还没抓到就把一条好材料永久丢掉。
- **标签先归一大小写再校验**：`pass` 与 `PASS` 是同一件事；表外的标签是格式错，这一档算失败，
  下一轮再问 —— 不猜一个「大概相关」。

### 24.3 `blocked` 是终态

`feed_items.relevance` 存三态小写（`pass|block|unknown`，AIHOT 的 `relevance`），
`feed_items.llm_stage` 存 `blocked`。`db.feed_items_pending_llm` 的第一条分支把 `blocked` 与
`full` 一起排除：判过就不再排进预算（否则每过 `retryHours` 就白问一次）。它也**不会发布** ——
没有中文标题摘要就没有 `written` 标记，页面按同一条门槛把它挡在外面。

本轮的日志里多了 `blocked` 一列：它是「这一轮丢掉的」而不是「这一轮写上的」，数进 `wrote` 会让
日志说写了四十条、而页面上一条都没变。

## 25 能力位接线：一档一个模型，没配就回落（2026-10-05 落，五期 2.3）

### 25.1 位子在哪

AIHOT `editorial/models.ts` 认 11 个能力位；我们认 9 个（`monitor` 不适用，`report` 归 5.7）。

| 能力位 | 谁在用 | 配置键 | 环境变量 |
| --- | --- | --- | --- |
| `prefilter` | `writing.write_one` 预筛支 | `llm.models.prefilter` | `CH_LLM_MODEL_PREFILTER` |
| `score` | `writing.write_one` 两次独立评分 | `llm.models.score` | `CH_LLM_MODEL_SCORE` |
| `understand` | `writing` 理解档 | `llm.models.understand` | `CH_LLM_MODEL_UNDERSTAND` |
| `summarize` | `writing` 便宜档 | `llm.models.summarize` | `CH_LLM_MODEL_SUMMARIZE` |
| `structure` | `writing` 结构档 | `llm.models.structure` | `CH_LLM_MODEL_STRUCTURE` |
| `translate` | `writing` 全文翻译 | `llm.models.translate` | `CH_LLM_MODEL_TRANSLATE` |
| `group` | `grouping._ask` 逐条关系判定 | `llm.models.group` | `CH_LLM_MODEL_GROUP` |
| `groupReview` | `grouping._ask(capability_key="groupReview")`：复核与并事件的第二遍 | `llm.models.groupReview` | `CH_LLM_MODEL_GROUP_REVIEW` |
| `digest` | `digest._ask` 事件综述 | `llm.models.digest` | `CH_LLM_MODEL_DIGEST` |

### 25.2 三条纪律

- 选择顺序与 AIHOT 相同：配置文件 → 环境变量 → 系统设置里那一个默认模型。没单独配就返回 `None`，
  交给 `llm.client` 用它的默认 —— 没配的机器行为与接线前完全一致。
- 每次现读、缓存一分钟：改完下一次调用生效，已经写完的不重判（AIHOT 同口径）。
- 页面与加载器走同一张表（`config.SYSTEM_KEYS` ↔ `forms.SYSTEM_LABELS`），`test_system_settings`
  盯着两边必须相等：加一个位要同时改两处，漏一处测试就红。

### 25.3 还没接的

`report`（日报周报月报）等 5.7 六期接了模型撰写再加位；AIHOT 的 `monitor`（Codex 重置公告）我们不做。
## 26 付费收据：一个逻辑请求只付一次钱（2026-10-05 落，五期 2.2）

对齐 AIHOT `providers/receipts.ts`。表 `llm_receipts` / `llm_receipt_attempts`（`SCHEMA_VERSION=25`），
代码 `api/app/llm/receipts.py`，接在 `llm.complete` 里。`llm_calls` 还是记账本，收据管的是「要不要再发一次请求」。

### 26.1 逻辑键：什么算「同一个请求」

`logical_key = service:purpose:model:sha256(stable_json(identity)):attempt_tag`。identity 里放的是模型、
提示词版本、消息、温度、上限、是否 JSON —— 这些一样就是同一个请求，发过一次就重放。

| 段 | 取值 | 说明 |
| --- | --- | --- |
| `service` | 固定 `llm` | |
| `purpose` | 档位名（`prefilter` / `score` / `translate` …） | |
| `model` | 没填时 `-` | |
| `identity` | 模型 + 提示词版本 + 消息 + 温度 + 上限 + json_mode | 换任一字段就是另一个请求 |
| `attempt_tag` | 没填时 `0` | **有意重问的唯一开关** |

**打分档必须带 `attempt_tag`**：两次评分的材料完全一样，不带就是第二次重放第一次的答案，均值变成一个数两次。
`writing.py` 的 `SCORE_CALLS` 传 `score-1` / `score-2`（AIHOT `analyze.ts` 同款）。

### 26.2 预算按 attempt 计

`llm.budgets`（环境变量 `CH_LLM_BUDGETS`，JSON）给 `(每分钟, 每小时, 每天)` 三个数：不配 = 不限，任一 ≤ 0 = 停。

预算数的是 `llm_receipt_attempts` 里 `origin='live'` 的行，所以**重试躲不过预算、重放不重复计费**。

### 26.3 四种情形与下次调用

| 情形 | 收据落成 | 下次调用 |
| --- | --- | --- |
| 拿到答案 | `received` → `completed` | 直接重放，不再发请求 |
| 端点明确拒绝：4xx/5xx、连不上、内容审核、答案用不了 | `failed` | 允许新 attempt，重新付钱 |
| 超时 / 连接中断 / 结果不明 | `pending` → `unknown` | 不自动重发，等放行 |
| 同一请求正在飞 | 不动 | 抛 `ReceiptBusy` |

「答案用不了」= 空消息或解析不出 JSON（`client._Unusable`）。账单照记（钱确实花了），收据落 `failed`，
让下一次重问能拿到新答案 —— AIHOT 的 `rejectReceivedResponse`。

### 26.4 陈旧与自动放行

| 阈值 | 动作 |
| --- | --- |
| `PENDING` 超过 10 分钟 | 标 `unknown`，抛 `ReceiptUnknown`（不猜它到底扣没扣钱） |
| `unknown` 超过 30 分钟 | 自动放行**一次**（attempt 上留 `AUTO_RELEASE_NOTE` 记号，第二次不再放） |

每轮 `writing.run()` 开头的 `receipts.recover()` 收拾上一轮留下的陈旧 `pending` 和到期 `unknown`。

### 26.5 没配预算的机器

行为与接线前一致：不限流、每个逻辑请求第一次照常发。收据只在「同一轮重跑 / 同材料重问」时省下钱。
## 27 判定材料与综述的写前核对：两处「形状就是判据」（2026-10-05 落，四期 4.12 / 五期 2.9）

### 27.1 综述写库前再核一遍输入（4.12）

AIHOT `composeStoryDigest` 在模型答案回来之后、写库之前，把两样东西再比一次：`stories.version` 与
`digestInputsHash`。对不上就把这次答案丢掉 —— 一段描述「另一批报道」的话写上去，比这一轮没写更坏，
而且它还会带着一份对不上的指纹落库，让下一次「输入没变」判在错的底稿上。

我们这边没有并发写者（一轮一个 asyncio 任务，抓取扔线程，`tick` 等它回来），所以 AIHOT 的
`pg_advisory_xact_lock` 没有对应物；缺的是**答案回来后再核一遍**这半步，现在已经补上：

| 位置 | 动作 |
| --- | --- |
| `digest.run` | `_ask` 返回后重算 `inputs_hash(db.feed_story_reports(id))`，与喂给模型的那一份比 |
| 对不上 | 不写库，`report["changed"] += 1`，记一条 `log.info`，下一轮按新输入重写 |

合并（`consolidate.merge`）与将来的纠错入口都从这条路走后，这条核对就是它们的兜底。

### 27.2 判定材料：一栏一行、带字段名（2.9）

AIHOT `relate.ts describeReport` 给模型的是**分栏的块**，不是挤成一行的一串：

```
【候选 C1】（该事实已有 3 篇报道；事实标题：…）
标题：…
来源：CoinDesk（当事方/官方）｜发布时间：…
摘要：…（截 360；没有写「（无）」）
事实要素：主体=…；动作=…；对象=…；日期=…（没有写「未知」）
```

形状本身是判据的一部分：一边有「事实要素」、另一边没有，或者摘要截 160 与截 360，判出来的关系就会
跟着变。所以：

| 事 | 在哪 |
| --- | --- |
| 渲染 | `grouping.describe`（`SUMMARY_CHARS = 360`）；待判那条与候选共用它 |
| 候选那侧多的一格 | `label="候选 Cn"` + `extra="（该事实已有 N 篇报道；事实标题：…）"` |
| 复核那一对 | `review` 用 `【报道 A】` / `【报道 B】` |
| 材料里带的数据 | `Candidate` 的 `first_party` / `subject` / `action` / `object` / `occurred_at` / `members` / `fact_title` |
| 四个装载点 | `stories.query_of`、`stories.pool`、`consolidate._view`、`db.feed_fact_pool` |

**换这个格式会整体动判定结果**：下一轮分组起，召回相同但模型给出的关系可能不同 —— 这是预期内的，
因为 AIHOT 喂的就是这一份材料。
## 28 分组侧的换版重判：旧规则定过的行不会自己重跑（2026-10-05 落，三期 4.11 / 五期 2.7）

提示词版本就是它的内容哈希，改一个字就是一个新版本。写作侧早就按档记 token（`writing.version`
配 `feed_items_pending_llm` 的 `versions` / `rewritten`），**分组侧原先没有**：一条报道定过组之后
就再也不问了，改了 `group-*.md` 之后，库里那几千行会一直用旧口径冒充新口径，而且完全静默。

### 28.1 记的是「这一站的版本」

| 事 | 在哪 |
| --- | --- |
| 版本 | `grouping.station_version()` = `group-batch.md` + `group-signal.md` + `group-pair.md` 三条哈希拼起来（AIHOT 的 `ANALYZE_PROMPT_VERSION = Object.values(PROMPT_VERSIONS).join("+")`） |
| 落库 | 每条定夺写进 `feed_item_facts.prompt_version` / `feed_story_signals.prompt_version`（`SCHEMA_VERSION=26`） |
| 单条定夺 | `stories.apply(..., version=)` / `stories._signal(..., version=)` |

### 28.2 挑出来重判

`db.feed_items_regroup(version, since, limit)` 挑「记着旧版本」的行，`db.feed_grouping_reset` 撤掉它
的自动归属，然后它们和新来的条目一起走同一条定夺路径 —— 撤掉之后它在池子里既不是候选也不算证据，
与 AIHOT 把重判中的报道标成 `regroup_pending` 是同一件事。

三条边界，都是有意的：

| 边界 | 为什么 |
| --- | --- |
| 排在新来的条目**之后** | 新来的先定；重判是补账（AIHOT 也把重判 job 排在活的报道后面） |
| 只取**召回窗口内**（14 天） | 重判要拿现在的池子当候选；窗口外的行在池子里已经没有自己那件事了，重判会把一条老报道变成一个**新**事件 |
| `prompt_version` 为空的不动 | 这次改动之前定的行（以及人工/测试写进去的）不重判 —— 上线那一刻把全库重算一遍，是拿一整轮模型钱换一次没有理由的重来 |

人工决定（`feed_grouping_overrides`）在查询那一侧就被排除：换提示词不该把人的决定重新掷一次骰子。

轮预算按 `maxItems` 分摊：一轮重判几条，下一轮接着挑，直到追平当前版本。

## 29 讨论帖回头重挂载：帖子先到、原文后到（2026-10-05 落，五期 2.10）

X 帖子常常比它讨论的原文早到：采集先看见帖子，判定站那一刻原文/事件还不存在，于是这条帖子被记成
`signal-unmatched`（`story_id IS NULL`）就一直躺着 —— 判定站只判一次，之后没有第二个人回头看它。
AIHOT `events/group.ts` 用两个窗口补这个口子，我们照做成 `stories._reattach`，每轮 `stories.run` 开头跑一次：

| 窗口 | AIHOT | 我们 | 依赖 |
| --- | --- | --- | --- |
| 新事实回头捞 | `rematchSignals`：6h 内新出现的事实，回头找未挂帖子 | 重算 `boosts` 后按 `embeddings.similarity >= SIGNAL_MIN_COSINE (0.72)` 再判一次 | 向量端点 |
| 等原帖出现 | `reclaimWaiting`：48h 内，回复/引用它的原帖出现时挂上去 | 按 `quoted_json` 里的 `/status/<id>` 粗筛出引用它的帖子，再判一次 | 无 |

1. 常量：`REMATCH_HOURS = 6` / `WAIT_HOURS = 48` / `REATTACH_LIMIT = 200`；查询走
   `db.feed_items_unattached_signals(since, quoted_id, limit)`（`story_id IS NULL`，窗口按 `observed_at`，排除
   `feed_grouping_overrides` 里的人工决定）。

2. 只在 `outcome in ("story", "development")` 时跑 —— 一条纯 `mention` 不进池子，扫它没意义。

3. 重试只吞一种失败：`llm.LLMUnavailable` 记一条 warning（对应 AIHOT `rematchError`/`reclaimError`），
   其他异常照常抛，不许静默。

4. 边界：没配向量端点时 `embeddings.warm` 整批回 `None`，「回头捞」这一半整条不执行（「等原帖」不依赖向量，照跑）；
   `REATTACH_LIMIT = 200` 是扫描上限；`report` 多两个数 `rematched` / `reclaimed`。

测试在 `api/tests/test_feed_signals.py`：早到的帖子在原帖出现后挂上、引用帖在原帖出现后挂上、
只有被引用的那一条会回头（不是全表重扫）。

## 30 身份守卫：模型能措辞，不能引入材料里没有的主体（2026-10-05 落，五期 3.12 + stripEcho）

一条讲 A 交易所的公告，模型顺手写成 B 交易所 —— 数字、时间、动作都对得上，只有主体错了。这种错
没人会专门去核（核的人得先知道该是谁），所以它必须在**落库前**被挡住，而不是靠人回头抽查。

AIHOT 的做法（`editorial/writing.ts`）：材料里出现过的公司进白名单，写完拿白名单裁一遍。

| 事 | AIHOT | 我们 |
| --- | --- | --- |
| 词表 | `industry/taxonomy.ts` 的 `IDENTITY_LEXICON`（模型厂商） | `app/feed/identity.py`（交易所 / 公链 / 发行方 / 监管机构），行业相关的，可增删 |
| 白名单 | 标题 / 正文 / 主推文 / 引用 / 来源名 + 发布域 + 来源账号主体 | 同上（来源账号主体等 `feed_sources` 有那个字段了再接） |
| 注入 | 摘要档提示词里的 `{{identity}}` 那一格 | `prompts/identity-context.md`，接在摘要档系统提示词后面（`_with_identity`） |
| 裁决 | 标题退回原标题（中文）或留空；摘要丢掉 | 同（`identity.Context.guard`） |
| 记账 | `identityGuard`，只在 fallback 时进 analysis | `feed_items.identity_guard`，只在 fallback 时有值（通过那一轮写空串清旧账） |

1. 白名单只认材料里真出现过的：少列一个主体只是少抓到一次错，多列一个会把写对了的标题也退回去，
   所以**币名不进词表**（`BNB` 是币不是主体）。
2. 发布域那一条是"正文只有一句话"时的兜底：`circle.com` 上的公告，发布方就是 Circle。
3. 版本：`summarize_version()` 把 `identity-context.md` 也算进去（AIHOT 同）。所以这一版上线后，
   按旧版写过的摘要档行会重跑一遍 —— 这是有意的，提示词确实变了。
4. 顺带补 `stripEcho`：模型有时把提示词里的行（`来源：`、`【已核验身份上下文】`、`原始标题：`）
   抄在答案末尾，只从**末尾往前**剥（中间出现的"来源："可能是正文的正常说法）；标题、摘要、
   译文正文三处都过一遍（AIHOT 在 `parseTranslateOutput` 的 summary/body 上做同一件事）。

测试在 `api/tests/test_feed_identity.py`：白名单来源、发布域兜底、连字符变体、标题回退与摘要丢弃、
账目落库、附则确实进了系统提示词，以及通过那一轮不留旧账。

## 31 行内标签占位符协议：模型只翻文字，记号一个不少（2026-10-05 落，五期 3.9 / 【新】正文图片列表）

正文里的链接、行内代码、图片带着机器要读的属性（`href`、`class="language-*"`、
`src`/`width`/`height`），直接交给模型翻会把它们改坏或吞掉。翻译档因此先 `shields` 后 `restore`：

1. `htmlbody.shields(body)` 按块切开，每块给一个 `Guarded`：媒体（`picture`/`video`/`img`）与 `code`
   换成 `⟦n⟧`，`<a href=…>` 换成 `<a id="Ln">`（原属性存在 `links` 里，是原块上的锚点，不是块外索引）；
2. `prompts/translate-body.md` 要求模型**逐字保留**这些记号：`⟦n⟧` 恰好出现一次、`<a id="Ln">` 只翻标签里的文字；
3. `htmlbody.unshield`/`restore` 逐块对账：记号少一个、多一个、重复、或模型自己编了一个，这一块就判 `None`
   —— 留原文、`body_complete=0`、`llm_stage` 停在 `understand`，下一轮再来补。**没有「猜一个最像的」这条路**：
   对账失败宁可留一块原文，也不把模型编的链接写进库；
4. 差值两种都要查：块数比替身多（模型漏块）与少（模型多写块）都算失败，所以 `restore` 拿的是 `guarded` 整表。

图片列表同一批落库：`htmlbody.images(body, limit=12)` 抽 1-12 张（`kind/url/width/height`，缺宽高是 `None`，
不是 0），源自带 `media` 时优先用源给的，写进 `feed_items.media_json` 的对象数组；老行是纯 URL 串，
`htmlbody.media_urls` 两种形状都读得回来（`input._media` / `sources/snapshot.py` 都走它）。API 层
（`api/app/api/v1/schemas.py` 的 `media: list[str]`、`web/src/api/types.gen.ts`）仍是 URL 串，没变。

AIHOT 对应 `editorial/translate.ts` 的 `shield`/`unshield` 与 `content/extract.ts` 的图片抽取；差别只剩
「对账失败重问一次」——我们直接留原文等下一轮（见 ALIGN-AIHOT §4.0 的 3.9）。

测试在 `api/tests/test_feed_htmlbody.py`（16 项）与 `api/tests/test_feed_writing.py`（保留链接与媒体、
丢记号块留原文且 `body_complete=0`）。

## 32 内容身份与版本：正文改了才重算（2026-10-05 落，五期 1.7）

AIHOT 在 `content/materials.ts` 里给每份材料一个内容身份：正文真正改了才算新一版，改版之前的模型结果只留档、不冒充新版（`stale`）。我们同样做法：

| 原语件 | 位置 |
| --- | --- |
| `collapse()` / `content_hash(title, body, excerpt)` | `feed/materials.py`（sha256，`\u0001` 分隔，与 AIHOT `contentHash` 逐字同口径） |
| `feed_items.content_hash` / `revision` / `llm_revision` | `store/schema.sql`（`SCHEMA_VERSION = 28`） |
| 旧版留档 `feed_item_revisions` | 同上（`source_id`+`external_id`+`revision` 主键） |
| 写入与推版 | `store/db.py` 的 `_next_revision` / `_archive_revision` / `feed_items_put` / `feed_items_set_detail` |
| 到期重排 | `db.feed_items_pending_llm` 第 4 条：`llm_revision <> revision`，不看 `retryHours` |

**四条不涨版规则**（任一命中就不算新版）：

1. 哈希相同；
2. 库里没基准（第一次看到）—— 只记基准，不把写过的行重算；
3. 这一版以前见过（来回改写法不算改版）；
4. 只差 U+FFFD —— 损坏字符当通配符，`same_barring_loss` 逐位比较。

**两个容易忘的地方**：

- `feed_items_put` 的正文与摘要用 coalesce（报告没带正文不许抹掉已补到的正文，AIHOT 的 `bodyText ?? existing.body_text`）。
- `feed_items_set_detail` 补到更长正文后也要重算 revision 并留档 —— 补正文就是改版。迁移时（升到 28）先把 `llm_revision` 回填成 `revision`，否则全库被判过期重跑。

测试在 `api/tests/test_feed_revision.py`（9 项）。

## 33 RSS 摘要与钩子文：写作站先等原文（2026-10-05 落，五期 1.4d/3.13）

一条只有标题、而链接可以去读的材料，现在问它就是在标题上写摘要 —— 而原文一到，这份就过期了，钱花两遍。所以抓页排在写作站之前，并且分清“没正文”与“读过但没读到”。

| 能力 | AIHOT | 我们 |
| --- | --- | --- |
| 正文 / 摘要分家 | `feedText`（`encoded`/`content` 算正文，`description`/`summary` 算摘要） | `sources/kind/rss.py` 的 `_CONTENT_TAGS` / `_SUMMARY_TAGS`；摘要存 `Discovery.excerpt` → `feed_items.excerpt`（上限 `EXCERPT_CHARS=2000`） |

## 34 收尾一批：队列、复合分析、资格台、报刊、推送、管理台、金标、MCP（2026-10-05 落）

`ALIGN-AIHOT.md` §3 清空的那一批。每一条只写「为什么是这个形状、换一种会怎样」。

### 34.1 补正文走队列，不走一个 for 循环（1.2）

一轮补正文要走好几分钟。循环版本把「欠哪几条」放在内存里，进程在这中间被杀掉，那批就没了 ——
而 `feed_items` 上什么都没写，下一轮只看新条目，它们**永远等不到**。

队列把这件事搬到表上（`feed_fetch_queue`）：一进队列就有行，认领时上租约，租约过期自动回到
`pending`。于是「崩了」变成「下一分钟接着跑」。三件配套的事各自的存在理由：

| 件 | 为什么非得有它 |
| --- | --- |
| 租约 | 没有它，一条正在读的会被第二个 tick 再读一遍；有它，崩在半路的那些到期就被回收 |
| 退避记在行上 | 坏链接每轮重新排队会把好条目的位置占掉。`attempts + next_try_at` 让「别再敲它」是数据，不是调用方的自觉 |
| 两个 job | `sources.poll` 每轮推它一把（预算也在这里刹），`sources.details` 是回收那一半 —— 没有过期租约时它什么都不做 |

预算与队列分工明确：**队列负责不丢，预算负责不冲**。`maxFetches` 还是每轮读几篇，它没有变成队列的
属性 —— 换一种（把预算也写进行上）会让「这一轮读几篇」变成一次写库，而它本来就是一台机器的刹车。

### 34.2 复合分析：盘点不立事件（4.9b）

一篇日报把十件事装在一起。它**是**一篇被发表过的东西，但它不是那十件事中任何一件的发生。

- 判定侧：`grouping.decide` 的 roundup 分支回 `role="mention"`，`mentions` 是它谈到的每一个候选。
- 落库侧：`feed_item_mentions` 记「提及」，`feed_items.analysis_scope = 'composite'` 记档位。一条报道
  仍然只能**属于**一个事实（`feed_item_facts` 的主键），所以「提及」必须是一张另一张表 —— 挤进同一张
  就等于说这篇盘点同时是十件事的证据。
- 读取侧：`views.collect` 把 composite 的条目从事件里摘出来（不立事件），但仍并进 `items`。
  全部动态照常显示它，热点榜与综述看不见它。
- 重判：`feed_items_for_grouping` 只收 `analysis_scope` 为空的行 —— 已经判过 primary 的不再重判。

一条补充规则写在提示词里（`group-batch.md` / `group-signal.md`）：`roundup` 的说明必须带上「只提及、
不立事件」，否则模型会以为它给出的是一个合并。

### 34.3 资格集中在一张表里（5.5）

「够不够格」原来散在 `rules.py` 的七八个谓词里，各处自己挑着调。`eligibility.py` 把它收成一份
有序的 `GATES`：每一道有名字、有人话说明、有它读的那几个字段、有一个纯函数。

顺序是内容的一部分：`withdrawn → released → pool → item_page → selectable → evidence → indexable
→ body_full → redistribute`。`evidence` 排在 `selectable` 之后，因为「是不是证据」只对已经够格的那
几条才值得问。

`GET /feed/eligibility` 与 `item_detail.eligibility` 读的是同一份 —— 页面说得出「卡在哪一道」，是
因为它印的就是那张表。

### 34.4 报刊的导语由模型写（5.7）

以前一期的「正文」是拼的：标题取第一条，每条各带一句类别模板。读起来像清单，不像一期刊物。

`prompts/edition.md` 一次写两样：这一期的标题（报头那一行）与一段导语。能力位是 `report`，与
AIHOT 同名。三件不能省：

1. **顺序不变**：排名与判词在进模型之前就定了，模型只写这两样文字。
2. **没模型不空**：`writing.enabled()` 为假、或这一趟模型不可用，`write_issue` 回 None，`compose`
   用规则版标题、导语留空。一期没有导语是少一段话，一期出不来是这一天的快照整个缺掉（9.7 的底线）。
3. **导语进 payload、不进列**：它是版面的一部分。标量是列、正文是 payload，一条事实只有一个地方记。

### 34.5 飞书推送：地址是 key，幂等在表上（5.8）

出口是一个 webhook 地址。它进 `feed_settings` 而不进 `config/` —— 它是一把 key，进 git 就等于公开。
台账里记的是它的**指纹**而不是明文，因为运维读口会把 `feed_deliveries` 翻出来。

三件各自的存在理由：

- 幂等在 `subject`（期号）上：同一期跑第二遍不会再发一条 —— 这件事由表保证，不由调用方记得。
- 退避记在行上（`next_try_at`，指数上升、封顶一小时）：进程重启不会把「别催它」丢掉。
- 没配地址时**一条都不认领**：认领了就得给它一个结局，而这里没有结局可给；地址配上之后那些行还在
  `pending` 上，下一趟自然会发。

空的一期不发：没有人需要被告知「这一天没事」。

### 34.6 管理台与口令（5.12）

设置页那个管理台面板已于 2026-10-05 移除（用户要求）：页面不再有登录框、本地键设置与换签名
密钥的入口。这一节的模型仍在，因为 `/run` 与 `/override` 的门靠它。

这台机器只有一个用户，所以「登录」不是账户体系：一把口令 + 一枚签过名的 cookie。口令在
`feed_settings['admin_password']`（或 `CH_ADMIN_PASSWORD`），签名密钥第一次用到时自动生成。

- cookie 里只有到期时刻与一枚 HMAC，没有口令本身 —— 一枚签过名的到期时间就是一张通行证。
- **没配口令 = 不设防**，而这个状态是读得出来的（`GET /feed/admin/session` 回 `guarded`），
  因为「设了口令」与「以为设了口令」之间的差别就是这个模块存在的理由。
- 回 401 而不是 403：它要的不是权限，是一次登录，而 401 是页面唯一会去弹登录框的那个码。
- 设了口令之后，改数据的入口（`/run`、`/override`、管理台设置、换签名密钥）都要先答对。
- 明文永不回浏览器：页面拿到的是掩码（开头几位 + 末几位）。

### 34.7 金标评测：只标有客观答案的那一部分（5.22）

「写得好不好」没有客观答案，所以它需要一个有客观答案的替身：一份人工标好的样本
(`eval_golden.json`) + 一个把机器答案与人对一遍的函数。它量的是**回归** —— 换了规则或提示词之后，
那些原本判对的还对不对。

标的是能被人对标的那 5 个轴（certainty / channel / pool / selectable / page），每一个都是纯函数，
答案唯一。**"这句话写得像不像中文" 不在这里**：它没有唯一答案，而让一个模型去评另一个模型写的话，
得到的是一个意见而不是一个读数。真要量那一块，需要的是另一批人手写的参考译文 —— 那份样本还没有，
所以这一节不假装有。

`GET /feed/eval` 只读、不写库、不调模型。回的是总数、过了几条、各轴的合格率，以及每一条没对上的
细节 ——「不合格」比「合格率 91%」更能告诉人改哪里。

### 34.8 MCP 出口：只读（routes/mcp）

`POST /api/mcp` 是一个只读的 MCP 服务端：JSON-RPC 2.0，四个方法（`initialize` / `tools/list` /
`tools/call` / `ping`）。工具就是我们自己的那几个读口，工具表在 `feed/mcp.py` 里定义一次。

**为什么只读**：对外的工具不叫任何付费的东西，也不改库。一个能被一串 token 叫醒的「跑一轮采集」
就是一个任何人都能按的计费按钮。

`tools/call` 回两份：一段给模型读的文本（`content`）与一份给程序读的结构（`structuredContent`）。
只给一份的话，另一边就要去猜 JSON 里哪一段是给它的。`GET /api/mcp` 回人读的那一份说明 ——
一个只能用 curl 的出口不是一个能被检查的出口。

### 34.9 SPA 的 catch-all 分两档（5.20b）

关于 / 隐私 / 联系三页已于 2026-10-05 移除：`site.PAGES`、`/feed/site*` 与 sitemap / llms.txt
里的地址一并删掉，左栏不再有那一行。

SPA 的 catch-all 分两档：末段不带点的路径回 `index.html`（那是 `/item/<id>` 这样的页），带点的回 404
（那是 `/favicon.ico` 这样的资源）。不分开的话，一个不存在的图片会回一页 HTML，而浏览器会把它当
图片解析失败 —— 排查时看到的是一个"坏图"，不是一个 404。

## 36 收尾第二批：引用、等重判、阅读位置（2026-10-05 落）

### 36.1 别人的原话单独译一遍（3.6）

一条 X 帖引了别人的一句话。那句话是**别人的原话** —— 混进正文一起译时，提示词把它读成这条帖子
自己的语气，而它往往正是这条帖子要反驳的那一句。

| 事 | 形状 | 为什么 |
| --- | --- | --- |
| 归谁译 | 单独一趟 `writing.translate_quotes`（活儿 `quotes.translate`，十分钟一趟） | 一句话的重试预算不该和正文那一批混在一起：正文一条几千字，这一句几十字 |
| 去重 | `feed_quote_translations` 的主键是**被引帖的号** | 十条帖子引同一句话只花一次钱；两处译文不一样，读的人会以为有人改口 |
| 帖子改了呢 | `text_hash` 是那句原文的指纹 | 同一条帖子被编辑过就重译，而不是把旧译文配新原文 |
| 它自己也收过 | `feed_quote_own_text` 直接拿那条条目自己的 `body_zh` | 同一条推文存两份译文，读起来是"它改口了" |
| 印在哪 | 写回每一条引用它的条目（`quoted_json.translation`） | 页面读的是条目上那一格；只存缓存表等于没做 |
| 什么不译 | 挖掉网址后不到 10 字，或者本来就是中文 | 译一遍只是把同一句话抄两遍 |

译文在上、原文在下：那句话不是我们写的，读者要能对回去。

### 36.2 还在等重判的那些，不算证据（4.8a）

提示词改一个字就是一个新版本，库里按旧版定过的行要重判；而重判是**有预算**的，所以总有一部分在
等 —— 等的时候，它身上那笔旧归属还在。

等的那些**不算证据**（`db._TRUSTED_EVIDENCE`，AIHOT 的 `recall.trusted`）：拿它去给别人当证据，
等于把旧口径借着别人再抄一遍。人工钉过的一直算 —— 人已经判过了，机器不该拿版本号把它算没。
`prompt_version` 为空的行（这套账之前定的）判不出来，按老行算。

只筛**召回池**（`feed_fact_pool`）这一处：它回答"这件事有谁在说"，是分组判定读的那一份。页面上的
桶、热度、综述输入都不筛 —— 那几条问的是"这件事里有哪几条"，一条等重判的报道仍然是这件事里的一
条，不该先在页面上消失。

### 36.3 换页再回来，还在原处（5.25）

折起来的那几天、停在屏幕上的那一条，记在会话语义里（`web/src/features/feed/restore.ts`）。

**刷新打开的那一次不恢复**（AIHOT 的 `isReload`）：一个滚到一半的旧列表会盖住顶上那几条新的，
而读者重开页面要的正是"现在有什么"。所以恢复只发生在**同一会话里换页再回来**时。

与 AIHOT 有一处不同：锚点找不到那一条时**什么都不做**，不退回去滚一个绝对像素 —— 列表只加载了
第一页的时候，一个原来合法的 `scrollY` 会把读者丢到空白处。

## 37 收尾第三批: 官方报道、正文目录、报刊要点与快讯 (2026-10-05 落)

三件都不是新栏目, 是把 AIHOT 已有的三处补上: 事件页缺"当事方自己怎么说", 详情页缺"长文怎么跳",
报刊缺"哪几条是要点、哪几条只够一行". 分法与锚点都在后端算, 页面只印.

### 37.1 事件页的官方报道 (`official_reports`)

| 问题 | 决定 | 为什么 |
| --- | --- | --- |
| 收哪些 | `first_party` 且不是讨论证据的那些, 最新在前, 截 12 | 与 `other_reports` 互补: 那边是别家怎么说它, 这边是它自己怎么说 |
| 与「谁在说」的关系 | 两边各按 `first_party` 滤一次 | 同一条不会在两栏里各印一遍 |
| 空的时候 | 不画那一栏 | 没有官方声音不是一条消息 |

### 37.2 详情页的正文目录 (`outline`)

1. **锚点**由 `htmlbody.with_outline` 给 h2–h4 依次编 `sec-N` 注进正文. 目录只收**有字**的标题,
   号码却照走 —— 号码错开一位, 目录点下去就落到别的节上.
2. **两份正文共用一套号**: 译文是照原文的块换的, 小标题在同样的位置, 所以切语言时目录不跳错.
   两边标题数对不上就**整块不给** —— 锚点指向不存在的那一节, 比没有目录更糟.
3. **少于两条不画**: 一条目录比正文还短时, 它不是导航, 是多出来的一行.
4. 页面点目录只滚到那个 id (`scrollToSection`), 不认标题文字 —— 目录与正文不可能对不上.

### 37.3 报刊的要点与快讯 (`highlights` / `flashes`)

一期在纸上分四块, **互斥**, 合起来正好是整期:

| 块 | 是什么 | 判据 |
| --- | --- | --- |

   印出日子, 没有就只印"上一期".
